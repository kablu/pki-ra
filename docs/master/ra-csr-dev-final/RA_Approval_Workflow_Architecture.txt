================================================================================
  1. OVERVIEW — MAKER-CHECKER MODEL
================================================================================

  This workflow uses a MAKER-CHECKER pattern:

  1. Client submits CSR → status = SUBMITTED
  2. ADMIN sees all requests → assigns to OPERATOR (Maker)
  3. MAKER reviews CSR → submits remarks → status = REVIEWED
  4. CHECKER (another operator) sees Maker's remarks →
     ACCEPTS or REJECTS → status = ACCEPTED / REJECTED
  5. ACCEPTED → sent to CA → ISSUED

  Rules:
    - Only ADMIN can see all CSR requests
    - Only ADMIN can assign a request to an operator
    - MAKER reviews and writes remarks (cannot accept/reject)
    - CHECKER sees Maker's remarks and accepts or rejects
    - The RA Operator who acts as the MAKER for a request is
      STRICTLY PROHIBITED from acting as the CHECKER for the
      same request. This is a mandatory separation of duties
      enforced at the application level. The system must reject
      any attempt by the Maker to accept or reject a request
      they have already reviewed.
    - Requester cannot be Maker or Checker

  2. ACTORS & ROLES
================================================================================

  +------------------+--------------------------------------------------+
  | Role             | Responsibilities                                 |
  +------------------+--------------------------------------------------+
  | CLIENT / USER    | Submits CSR (REST / EST / SCEP / CMP)            |
  |                  | Downloads issued certificate                     |
  +------------------+--------------------------------------------------+
  | ROLE_ADMIN       | Sees ALL submitted CSR requests                  |
  |                  | Assigns request to an Operator (Maker)           |
  |                  | Selects operator from dropdown                   |
  |                  | Can also act as Maker or Checker if needed       |
  +------------------+--------------------------------------------------+
  | ROLE_OPERATOR    | Acts as MAKER or CHECKER (not both on same req)  |
  | (Maker)          | Reviews CSR, writes remarks, submits review      |
  +------------------+--------------------------------------------------+
  | ROLE_OPERATOR    | Sees Maker's remarks                             |
  | (Checker)        | Accepts or Rejects the request                   |
  +------------------+--------------------------------------------------+
  | ROLE_AUDITOR     | Read-only access to all requests + audit logs    |
  +------------------+--------------------------------------------------+


================================================================================
  3. STATE MACHINE — REQUEST LIFECYCLE
================================================================================

  CSR Submitted
       |
       v
  [SUBMITTED] -----> Admin assigns to Operator (Maker)
       |
       v
  [ASSIGNED] ------> Maker reviews + writes remarks
       |
       v
  [REVIEWED] ------> Checker sees remarks
       |
       +----------+----------+
       |                     |
       v                     v
  [ACCEPTED]            [REJECTED]
       |                     |
       v                     v
  Send to CA            Notify requester
       |                (with rejection reason)
       +--------+
       |        |
       v        v
  [ISSUED]  [FAILED]
       |
       v
  [ACTIVE]


  STATE DEFINITIONS:

  +-----------------+---------------------------------------------------+
  | State           | Description                                       |
  +-----------------+---------------------------------------------------+
  | SUBMITTED       | CSR received, 7-layer validation passed,          |
  |                 | waiting for Admin to assign                       |
  +-----------------+---------------------------------------------------+
  | ASSIGNED        | Admin assigned to a Maker (operator),              |
  |                 | waiting for Maker to review                       |
  +-----------------+---------------------------------------------------+
  | REVIEWED        | Maker submitted review with remarks,               |
  |                 | waiting for Checker to accept or reject            |
  +-----------------+---------------------------------------------------+
  | ACCEPTED        | Checker accepted, sending to CA for signing        |
  +-----------------+---------------------------------------------------+
  | REJECTED        | Checker rejected (with reason)                     |
  |                 | Requester notified, request closed                |
  +-----------------+---------------------------------------------------+
  | ISSUED          | CA signed successfully, certificate stored          |
  +-----------------+---------------------------------------------------+
  | FAILED          | CA signing failed (network/config error)           |
  |                 | Can be retried by Admin                           |
  +-----------------+---------------------------------------------------+

  VALID TRANSITIONS:

  +-------------------+---> +-------------------+--- Who ----------+
  | From              |     | To                |                   |
  +-------------------+     +-------------------+-------------------+
  | SUBMITTED         | --> | ASSIGNED          | Admin assigns     |
  | ASSIGNED          | --> | REVIEWED          | Maker submits     |
  | REVIEWED          | --> | ACCEPTED          | Checker accepts   |
  | REVIEWED          | --> | REJECTED          | Checker rejects   |
  | ACCEPTED          | --> | ISSUED            | CA signs OK       |
  | ACCEPTED          | --> | FAILED            | CA error          |
  | FAILED            | --> | ACCEPTED          | Admin retries     |
  +-------------------+     +-------------------+-------------------+

  INVALID TRANSITIONS (blocked in code):

  | SUBMITTED → REVIEWED   | Cannot skip assignment              |
  | SUBMITTED → ACCEPTED   | Cannot skip Maker + Checker         |
  | ASSIGNED  → ACCEPTED   | Cannot skip Maker review            |
  | REJECTED  → ACCEPTED   | Final state, must resubmit CSR      |
  | ISSUED    → REJECTED   | Cannot un-issue (use revocation)    |

  STEP 3: ADMIN ASSIGNS REQUEST TO OPERATOR (MAKER)
  =================================================================
    API:    POST /api/ra/requests/{id}/assign
    Auth:   ROLE_ADMIN only
    Body:   { "operatorId": 5 }
            (operator selected from dropdown in UI)

    System:
      a. Validate: status == SUBMITTED
      b. Validate: operatorId exists, is_active, has ROLE_OPERATOR
      c. Validate: operator != requester
      d. Update: status = ASSIGNED,
                 assigned_to_id = 5,
                 assigned_at = now,
                 assigned_by_id = admin.id
      e. Audit: CSR_ASSIGN (resource=101, desc="Assigned to priya.patel")

    Response: 200 OK

        "assignedTo": "priya.patel", ... }

  STEP 6: MAKER REVIEWS AND SUBMITS REMARKS
  =================================================================
    API:    POST /api/ra/requests/{id}/review
    Auth:   ROLE_OPERATOR (must be the assigned Maker)
    Body:   {
              "remarks": "CSR verified. Subject DN matches CMDB entry.
                          Key size 4096 meets policy. SANs valid.
                          Recommend approval."
            }

    System:
      a. Validate: status == ASSIGNED
      b. Validate: current user == assigned_to_id (only Maker can review)
      c. Update: status = REVIEWED,
                 maker_remarks = body.remarks,
                 maker_reviewed_at = now
      d. Audit: CSR_REVIEW (resource=101, desc="Maker reviewed with remarks")
      e. Notify: all ROLE_OPERATOR except Maker
         "CSR #101 reviewed by priya.patel — pending your acceptance"

    Response: 200 OK
      { "id": 101, "status": "REVIEWED",
        "makerRemarks": "CSR verified...",
        "makerUsername": "priya.patel",
        "makerReviewedAt": "2026-06-23T11:00:00Z" }


  STEP 7: CHECKER VIEWS REVIEWED REQUESTS
  =================================================================
    API:    GET /api/ra/requests?status=REVIEWED
    Auth:   ROLE_OPERATOR (excludes requests where current user is Maker)

    Response: list of reviewed requests (not assigned to this operator)
      [{
        "id": 101,
        "subjectDn": "CN=api.example.com",
        "status": "REVIEWED",
        "makerUsername": "priya.patel",
        "makerRemarks": "CSR verified. Subject DN matches...",
        "makerReviewedAt": "2026-06-23T11:00:00Z"
      }]


  STEP 8A: CHECKER ACCEPTS
  =================================================================
    API:    POST /api/ra/requests/{id}/accept
    Auth:   ROLE_OPERATOR (must NOT be the Maker)
    Body:   { "remarks": "Agreed with Maker's assessment. Approved." }

    CRITICAL VALIDATION — SEPARATION OF DUTIES:
      The RA Operator who acted as the Maker (reviewed this request
      and submitted remarks) is strictly prohibited from acting as
      the Checker. The system compares the current user's ID against
      the assigned_to_id field. If they match, the request is
      rejected with HTTP 403 (PKI_APR_005: "The operator who
      reviewed this request cannot accept or reject it. A different
      operator must perform the Checker role.").

    System:
      a. Validate: status == REVIEWED
      b. Validate: current user != assigned_to_id (Checker != Maker)
         → FAIL: 403 PKI_APR_005 — separation of duties violation
      c. Validate: current user != requester
      d. Update: status = ACCEPTED,
                 checker_id = current_user.id,
                 checker_decision = ACCEPTED,
                 checker_remarks = body.remarks,
                 checker_decided_at = now
      e. Audit: CSR_ACCEPT (resource=101)
      f. AUTO-ISSUE: send CSR to CA
           --> CaClient.sign(csrPem, validityDays, sans)
           --> Save certificate, update status = ISSUED
      g. Audit: CERT_ISSUE
      h. Notify: requester "Your certificate has been issued"

    Response: 200 OK
      { "id": 101, "status": "ISSUED",
        "certificateSerial": "4F2A1B3C...",
        "checkerUsername": "vikram.singh",
        "checkerRemarks": "Agreed with Maker's assessment..." }


  STEP 8B: CHECKER REJECTS
  =================================================================
    API:    POST /api/ra/requests/{id}/reject
    Auth:   ROLE_OPERATOR (must NOT be the Maker)
    Body:   { "remarks": "Domain not in approved list. Rejecting." }

    CRITICAL VALIDATION — SEPARATION OF DUTIES:
      Same rule as accept — the Maker operator cannot reject the
      request either. A different operator must perform this action.

    System:
      a. Validate: status == REVIEWED
      b. Validate: current user != assigned_to_id (Checker != Maker)
         → FAIL: 403 PKI_APR_005 — separation of duties violation
      c. Update: status = REJECTED,
                 checker_id = current_user.id,
                 checker_decision = REJECTED,
                 checker_remarks = body.remarks,
                 checker_decided_at = now,
                 status_reason = body.remarks
      d. Audit: CSR_REJECT (resource=101)
      e. Notify: requester + Maker
         "CSR #101 rejected by vikram.singh: Domain not in approved list"

    Response: 200 OK
      { "id": 101, "status": "REJECTED",
        "checkerUsername": "vikram.singh",
        "checkerRemarks": "Domain not in approved list..." }

  KEY RULES:
    1. The RA Operator who performed the Maker role (reviewed the
       request and submitted remarks) is STRICTLY PROHIBITED from
       acting as the Checker for the same request. This is the
       fundamental separation of duties principle — no single
       operator can both review and approve/reject a certificate
       request. The system enforces this at the API level by
       comparing the current user's ID against the assigned_to_id
       (Maker) before allowing accept or reject operations. Any
       violation returns HTTP 403 with error PKI_APR_005.
    2. Requester cannot be Maker or Checker
    3. Only Admin can assign (select from operator dropdown)
    4. Only assigned Maker can submit review
    5. Any operator EXCEPT the Maker can be Checker

  | Checker accepts               | Requester        | Email + In-App        |
  | Checker rejects               | Requester + Maker| Email + In-App        |

  | Issuance failed               | Maker + Checker  | Email + In-App        |

  10. ERROR CODES
================================================================================

  +-------------------+-----+----------------------------------------+
  | Code              | HTTP| Message                                |
  +-------------------+-----+----------------------------------------+
  | PKI_APR_001       | 400 | Request is not in correct status        |
  | PKI_APR_002       | 403 | Cannot review your own request          |
  | PKI_APR_003       | 403 | Only Admin can assign requests          |
  | PKI_APR_004       | 403 | Only assigned Maker can submit review   |
  | PKI_APR_005       | 403 | The operator who reviewed this request   |
  |                   |     | cannot accept or reject it. A different  |
  |                   |     | operator must perform the Checker role.  |
  |                   |     | (Separation of duties violation)         |
  | PKI_APR_006       | 403 | Requester cannot be Maker or Checker    |
  | PKI_APR_007       | 404 | Operator not found                      |
  | PKI_APR_008       | 400 | Remarks are required for review         |
  | PKI_APR_009       | 400 | Request not assigned to you             |
  +-------------------+-----+----------------------------------------+

  TEST-01: Happy Path — Submit → Assign → Review → Accept → Issue
  -------------------------------------------------------------------
    1. POST /requests (user: rahul) → 201, status=SUBMITTED

    5. GET /requests/my-assigned (user: priya) → sees #101
    6. POST /requests/101/review (priya, remarks="OK") → REVIEWED
    7. GET /requests/pending-check (user: vikram) → sees #101
    8. POST /requests/101/accept (vikram) → ISSUED
    9. Audit: CSR_SUBMIT, CSR_ASSIGN, CSR_REVIEW, CSR_ACCEPT, CERT_ISSUE

  TEST-02: Reject Path
  -------------------------------------------------------------------
    1-6. Same as TEST-01 (up to REVIEWED)
    7. POST /requests/101/reject (vikram, remarks="Bad domain") → REJECTED
    8. Audit: CSR_REJECT
    9. Notification sent to requester + Maker

    1-6. Same (Maker = priya)
    7. POST /requests/101/accept (user: priya) → 403 PKI_APR_005

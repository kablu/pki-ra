================================================================================
  1. PURPOSE & BUSINESS NEED
================================================================================

  Why Approval Workflow Exists:
  -----------------------------------------------------------------------
  A certificate is a TRUST document. Once issued, it represents the
  identity of a server, device, or person. A wrong certificate in the
  wrong hands = security breach.

  The approval workflow ensures:
    - NO certificate is issued without authorized human/policy review
    - HIGH-RISK certificates get MULTIPLE levels of approval
    - LOW-RISK certificates get FAST automated approval
    - Every decision is AUDITED with who, when, why
    - ABSENT approvers don't block the pipeline (delegation)
    - STALE requests don't rot forever (escalation/timeout)

  Business Impact:
    Without workflow:
      Any employee submits CSR → certificate issued immediately
      → No oversight → wildcard cert for *.production.com issued
      → Key compromise → $2M incident

    With workflow:
      Employee submits CSR → policy check → operator reviews →
      security officer approves (for wildcard) → certificate issued
      → Full audit trail → zero unauthorized certificates


================================================================================
  2. APPROVAL WORKFLOW MODELS
================================================================================

  The RA supports 4 approval models. Each is used based on the
  certificate template's risk level and organizational policy.


  MODEL A — SINGLE APPROVAL (Phase 1, Currently Implemented)
  -----------------------------------------------------------------------

    Flow:
      Requester --> CSR --> [7-Layer Validation] --> PENDING
                                                      |
                                          Operator/Admin reviews
                                                      |
                                          +-----------+-----------+
                                          |                       |
                                       APPROVE                 REJECT
                                          |                       |
                                          v                       v
                                     Send to CA             REJECTED
                                          |              (with reason)
                                          v
                                       ISSUED

    When to use:
      - Standard TLS Server certificates
      - Internal client certificates
      - Default for most templates

    Who can approve:
      - ROLE_OPERATOR
      - ROLE_ADMIN

    Rules:
      - Requester CANNOT approve their own request
      - One approval is sufficient
      - Decision is final and immutable


  MODEL B — AUTO-APPROVE (Phase 2, Template-Based)
  -----------------------------------------------------------------------

    Flow:
      Requester --> CSR --> [7-Layer Validation] --> Template check
                                                      |
                                          Template.auto_approve = true?
                                                      |
                                          +-----------+-----------+
                                          |                       |
                                         YES                     NO
                                          |                       |
                                          v                       v
                                    System auto-approves    → MODEL A/C
                                    (approver = "system")   (manual flow)
                                          |
                                          v
                                     Send to CA
                                          |
                                          v
                                       ISSUED

    When to use:
      - Dev/test environment certificates
      - Short-lived certificates (<30 days)
      - Internal mTLS between microservices
      - Renewal of existing certificates (simplereenroll)

    Conditions for auto-approve (configurable per template):
      - Template.auto_approve = true
      - Requester has specific role (e.g., ROLE_OPERATOR)
      - CSR matches a pre-approved DN pattern
      - Certificate type is low-risk
      - Renewal (not first-time issuance)

    Audit:
      - Auto-approval logged with approver = "system"
      - reason = "Auto-approved: template policy"


  MODEL C — MULTI-LEVEL APPROVAL (Phase 5, Enterprise)
  -----------------------------------------------------------------------

    Flow:
      Requester --> CSR --> [7-Layer Validation] --> PENDING
                                                      |
                                          Level 1: Team Lead / Operator
                                          reviews and approves
                                                      |
                                                      v
                                                 PENDING_L2
                                                      |
                                          Level 2: Security Officer
                                          reviews and approves
                                                      |
                                                      v
                                                 PENDING_L3
                                                      |
                                          Level 3: (if configured)
                                          CA Manager / CISO approves
                                                      |
                                                      v
                                              FULLY_APPROVED
                                                      |
                                                      v
                                                 Send to CA
                                                      |
                                                      v
                                                   ISSUED

    At ANY level, if REJECTED:
      --> Request status = REJECTED
      --> All subsequent levels skipped
      --> Requester notified with reason

    When to use:
      - Code Signing certificates (high-risk)
      - Wildcard certificates (*.production.com)
      - External-facing certificates
      - CA cross-certification requests
      - High-value certificates (long validity, wide scope)

    Approval chain defined in approval_policies table:
      [
        {"level": 1, "role": "ROLE_OPERATOR", "count": 1},
        {"level": 2, "group": "security-team", "count": 1},
        {"level": 3, "role": "ROLE_ADMIN", "count": 1}
      ]

    Rules:
      - Each level must be completed before next level begins
      - Same person cannot approve at multiple levels
      - Requester cannot approve at any level
      - If a level requires count=2, TWO different people must approve


  MODEL D — DELEGATION (Phase 5, Absence Management)
  -----------------------------------------------------------------------

    Flow:
      Operator A is on leave (2026-07-01 to 2026-07-15)
      Operator A creates delegation to Operator B

      During delegation period:
        Requester --> CSR --> PENDING
                                |
                    Operator A is original approver
                    but Operator A is absent
                                |
                    System checks: delegation exists?
                    Operator A delegated to Operator B? YES
                    Delegation still valid (within date range)? YES
                                |
                    Operator B sees the request in "My Pending" queue
                    Operator B approves on behalf of Operator A
                                |
                    Audit log: "Approved by Operator B
                               (delegated from Operator A)"
                                |
                             APPROVED --> CA --> ISSUED

    When to use:
      - Vacation / leave coverage
      - Temporary role transfer
      - Business continuity

    Rules:
      - Delegation has valid_from and valid_until (date range)
      - Delegate must have same or higher role
      - Delegate cannot re-delegate (no chain delegation)
      - Delegation can be revoked early by delegator or admin
      - Expired delegations are automatically ignored


================================================================================
  3. STATE MACHINE — REQUEST LIFECYCLE
================================================================================

  COMPLETE STATE DIAGRAM:

                                     CSR Submitted
                                          |
                                          v
                  +--- Auto-approve? --[PENDING]-- Manual? ---+
                  |        YES                       NO       |
                  v                                           v
          [AUTO_APPROVED]                             [PENDING_L1]
                  |                                           |
                  |                              L1 approves  |  L1 rejects
                  |                                  |        |      |
                  |                                  v        |      v
                  |                           [PENDING_L2]    |  [REJECTED]
                  |                                  |        |
                  |                     L2 approves  |  L2 rejects
                  |                         |        |      |
                  |                         v        |      v
                  |                  [PENDING_L3]    |  [REJECTED]
                  |                         |        |
                  |            L3 approves  |  L3 rejects
                  |                |        |      |
                  |                v        |      v
                  |         [FULLY_APPROVED] |  [REJECTED]
                  |                |         |
                  +-------+-------+---------+
                          |
                          v
                    [SEND_TO_CA]
                          |
                +---------+---------+
                |                   |
                v                   v
            [ISSUED]            [FAILED]
                |                   |
                v                   v
            [ACTIVE]          (Can retry)
                |
        +-------+-------+
        |       |       |
        v       v       v
   [REVOKED] [SUSPENDED] [EXPIRED]
                |
                v
            [ACTIVE]
          (unsuspend)


  STATE DEFINITIONS:

  +-----------------------+-------+----------------------------------------+
  | State                 | Phase | Description                            |
  +-----------------------+-------+----------------------------------------+
  | PENDING               |   1   | Submitted, awaiting first approval     |
  | PENDING_L1            |   5   | Alias for PENDING in multi-level       |
  | PENDING_L2            |   5   | Level 1 approved, awaiting Level 2     |
  | PENDING_L3            |   5   | Level 2 approved, awaiting Level 3     |
  | AUTO_APPROVED         |   2   | System auto-approved per template      |
  | FULLY_APPROVED        |   5   | All required levels approved           |
  | APPROVED              |   1   | Approved (single-level), sending to CA |
  | REJECTED              |   1   | Denied at any level (with reason)      |
  | ISSUED                |   1   | CA signed, certificate stored          |
  | FAILED                |   1   | CA signing failed (can retry)          |
  | EXPIRED_REQUEST       |   5   | Not approved within timeout period     |
  +-----------------------+-------+----------------------------------------+

  CERTIFICATE STATES (after issuance):

  +-----------------------+-------+----------------------------------------+
  | State                 | Phase | Description                            |
  +-----------------------+-------+----------------------------------------+
  | ACTIVE                |   1   | Certificate in use, valid              |
  | REVOKED               |   3   | Permanently revoked (with reason)      |
  | SUSPENDED             |   3   | Temporary hold (can be unsuspended)    |
  | EXPIRED               |   3   | Validity period ended                  |
  +-----------------------+-------+----------------------------------------+

  VALID STATE TRANSITIONS:

  +-------------------+---> +-------------------+--- Trigger ----------+
  | From              |     | To                |                      |
  +-------------------+     +-------------------+----------------------+
  | PENDING           | --> | APPROVED          | Single-level approve |
  | PENDING           | --> | PENDING_L2        | Multi-level L1 done  |
  | PENDING           | --> | AUTO_APPROVED     | Template auto-approve|
  | PENDING           | --> | REJECTED          | Operator rejects     |
  | PENDING           | --> | EXPIRED_REQUEST   | Timeout exceeded     |
  | PENDING_L2        | --> | PENDING_L3        | L2 approved          |
  | PENDING_L2        | --> | REJECTED          | L2 rejects           |
  | PENDING_L3        | --> | FULLY_APPROVED    | L3 approved          |
  | PENDING_L3        | --> | REJECTED          | L3 rejects           |
  | APPROVED          | --> | ISSUED            | CA signed OK         |
  | APPROVED          | --> | FAILED            | CA signing error     |
  | AUTO_APPROVED     | --> | ISSUED            | CA signed OK         |
  | FULLY_APPROVED    | --> | ISSUED            | CA signed OK         |
  | FAILED            | --> | APPROVED          | Retry after fix      |
  | ISSUED/ACTIVE     | --> | REVOKED           | Admin revokes        |
  | ISSUED/ACTIVE     | --> | SUSPENDED         | Admin suspends       |
  | ISSUED/ACTIVE     | --> | EXPIRED           | Time passed          |
  | SUSPENDED         | --> | ACTIVE            | Admin unsuspends     |
  | SUSPENDED         | --> | REVOKED           | Admin revokes        |
  +-------------------+     +-------------------+----------------------+

  INVALID TRANSITIONS (must be blocked in code):

  +-------------------+-/-> +-------------------+--- Why blocked ------+
  | REJECTED          | --> | APPROVED          | Final state, resubmit|
  | ISSUED            | --> | PENDING           | Cannot un-issue      |
  | REVOKED           | --> | ACTIVE            | Revocation is final  |
  | EXPIRED           | --> | ACTIVE            | Cannot un-expire     |
  | PENDING_L2        | --> | PENDING           | Cannot go backwards  |
  +-------------------+     +-------------------+----------------------+

  MODEL A — SINGLE APPROVAL (Detailed Steps)
  =======================================================================

  Actors:
    Requester: rahul.sharma (ROLE_OPERATOR)
    Approver:  priya.patel (ROLE_ADMIN)

  Step 1: REQUESTER SUBMITS CSR
  -------------------------------------------------------------------
    API:    POST /api/ra/requests
    Auth:   HTTP Basic (rahul.sharma)
    Body:   { "pkcs10": "-----BEGIN CERTIFICATE REQUEST-----...",
              "validityDays": 365 }

    System actions:
      a. Resolve identity: rahul.sharma --> users.id = 1
      b. Run 7-layer validation (L1-L7)
      c. All pass --> save to DB:
           certificate_requests (
             id=101, csr_pem=..., subject_dn="CN=api.acme.com",
             key_algorithm="RSA", key_size=4096,
             status="PENDING", requester_id=1
           )
      d. Audit log:
           username=rahul.sharma, action=CSR_SUBMIT,
           resource_id=101, outcome=SUCCESS
      e. Notify approvers:
           "New CSR pending: CN=api.acme.com (request #101)"

    Response: 201 Created
      { "id": 101, "status": "PENDING",
        "subjectDn": "CN=api.acme.com", ... }

  Step 2: APPROVER VIEWS PENDING REQUESTS
  -------------------------------------------------------------------
    API:    GET /api/ra/requests?status=PENDING
    Auth:   HTTP Basic (priya.patel)

    Response: 200 OK
      { "content": [
          { "id": 101, "subjectDn": "CN=api.acme.com",
            "keyAlgorithm": "RSA", "keySize": 4096,
            "requesterUsername": "rahul.sharma",
            "status": "PENDING", "createdAt": "2026-06-20T10:00:00Z" }
        ], "totalElements": 1 }

  Step 3: APPROVER REVIEWS REQUEST DETAILS
  -------------------------------------------------------------------
    API:    GET /api/ra/requests/101
    Auth:   HTTP Basic (priya.patel)

    Response: 200 OK
      { "id": 101, "subjectDn": "CN=api.acme.com,O=Acme,C=IN",
        "keyAlgorithm": "RSA", "keySize": 4096,
        "subjectAltNames": "dns:api.acme.com,dns:api2.acme.com",
        "requestedValidityDays": 365, "status": "PENDING",
        "requesterUsername": "rahul.sharma",
        "createdAt": "2026-06-20T10:00:00Z",
        "approvals": [] }

  Step 4A: APPROVER APPROVES
  -------------------------------------------------------------------
    API:    POST /api/ra/requests/101/approve
    Auth:   HTTP Basic (priya.patel)
    Body:   { "comment": "Verified: api.acme.com belongs to payment team" }

    System actions:
      a. Validate: request status == PENDING? YES
      b. Validate: approver != requester? YES (priya != rahul)
      c. Validate: approver has ROLE_ADMIN or ROLE_OPERATOR? YES
      d. Save approval decision:
           certificate_request_approvals (
             request_id=101, approver_id=2,
             decision="APPROVED",
             comment="Verified: api.acme.com belongs to payment team"
           )
      e. Update request: status = APPROVED
      f. Audit log:
           username=priya.patel, action=CSR_APPROVE,
           resource_id=101, outcome=SUCCESS
      g. AUTO-ISSUE: send CSR to CA
           --> CaClient.sign(csrPem, validityDays, sans)
           --> CA returns signed certificate
      h. Save certificate:
           certificates (
             serial_number="4F2A1B3C...",
             subject_dn="CN=api.acme.com",
             status="ACTIVE", request_id=101
           )
      i. Update request: status = ISSUED, certificate_id = (new cert id)
      j. Audit log:
           username=priya.patel, action=CERT_ISSUE,
           resource_id="4F2A1B3C...", outcome=SUCCESS
      k. Notify requester:
           "Your certificate has been issued: CN=api.acme.com"

    Response: 200 OK
      { "id": 101, "status": "ISSUED",
        "certificateSerial": "4F2A1B3C...", ... }

  Step 4B: APPROVER REJECTS (alternative)
  -------------------------------------------------------------------
    API:    POST /api/ra/requests/101/reject
    Auth:   HTTP Basic (priya.patel)
    Body:   { "comment": "Domain api.acme.com not registered in CMDB" }

    System actions:
      a. Validate: status == PENDING? YES
      b. Save rejection:
           certificate_request_approvals (
             request_id=101, approver_id=2,
             decision="REJECTED",
             comment="Domain api.acme.com not registered in CMDB"
           )
      c. Update request:
           status = REJECTED,
           status_reason = "Domain api.acme.com not registered in CMDB"
      d. Audit log:
           username=priya.patel, action=CSR_REJECT,
           resource_id=101, outcome=SUCCESS
      e. Notify requester:
           "Your request #101 was rejected: [reason]"

    Response: 200 OK
      { "id": 101, "status": "REJECTED",
        "statusReason": "Domain api.acme.com not registered..." }


  MODEL B — AUTO-APPROVE (Detailed Steps)
  =======================================================================

  Step 1: REQUESTER SUBMITS CSR (same as Model A)

  Step 2: SYSTEM CHECKS AUTO-APPROVE CONDITIONS
  -------------------------------------------------------------------
    System actions:
      a. Determine template (from CSR content or explicit template_id)
      b. Load approval_policy for this template
      c. Check auto_approve_conditions:
           {
             "conditions": [
               {"type": "role", "value": "ROLE_OPERATOR"},
               {"type": "dn_pattern", "value": "CN=*.dev.acme.internal"},
               {"type": "max_validity_days", "value": 90},
               {"type": "renewal", "value": true}
             ],
             "match_mode": "ALL"
           }
      d. Requester has ROLE_OPERATOR? YES ✅
      e. DN matches *.dev.acme.internal? YES ✅
      f. Validity <= 90 days? YES ✅
      g. ALL conditions met --> AUTO-APPROVE

  Step 3: SYSTEM AUTO-APPROVES
  -------------------------------------------------------------------
    System actions:
      a. Save auto-approval:
           certificate_request_approvals (
             request_id=102, approver_id=NULL,
             decision="APPROVED",
             comment="Auto-approved: template policy (dev-tls-short)"
           )
      b. Update request: status = APPROVED
      c. Audit log:
           username=system, action=CSR_AUTO_APPROVE,
           resource_id=102, outcome=SUCCESS,
           description="Auto-approved by template policy: dev-tls-short"
      d. Immediately send to CA --> issue certificate
      e. Audit log: CERT_ISSUE

    Total time: < 5 seconds (no human wait)


  MODEL C — MULTI-LEVEL APPROVAL (Detailed Steps)
  =======================================================================

  Scenario: Code Signing certificate — requires 3 approvals

  Approval Policy:
    {
      "name": "code-signing-policy",
      "template_id": 3,
      "approval_chain": [
        {"level": 1, "role": "ROLE_OPERATOR", "count": 1,
         "description": "Team lead verifies requester identity"},
        {"level": 2, "group": "security-team", "count": 1,
         "description": "Security officer reviews code signing scope"},
        {"level": 3, "role": "ROLE_ADMIN", "count": 1,
         "description": "CA manager gives final authorization"}
      ],
      "escalation_hours": 48
    }

  Step 1: REQUESTER SUBMITS CSR
    status = PENDING (current_approval_level = 1)
    Notify: all ROLE_OPERATOR users

  Step 2: LEVEL 1 — Team Lead Approves
  -------------------------------------------------------------------
    API:    POST /api/ra/requests/103/approve
    Auth:   amit.kumar (ROLE_OPERATOR)
    Body:   { "comment": "Identity verified, requester is authorized" }

    System actions:
      a. Validate: current_approval_level == 1? YES
      b. Validate: amit.kumar has ROLE_OPERATOR? YES
      c. Save approval (level=1)
      d. Check: level 1 complete? (count=1, got 1) YES
      e. Advance: current_approval_level = 2, status = PENDING_L2
      f. Set escalation_deadline = now + 48 hours
      g. Audit log: CSR_APPROVE_L1
      h. Notify: security-team group members
           "Request #103 needs Level 2 security review"

  Step 3: LEVEL 2 — Security Officer Approves
  -------------------------------------------------------------------
    API:    POST /api/ra/requests/103/approve
    Auth:   sneha.gupta (member of security-team group)
    Body:   { "comment": "Code signing scope acceptable for internal use" }

    System actions:
      a. Validate: current_approval_level == 2? YES
      b. Validate: sneha.gupta in approval_groups "security-team"? YES
      c. Validate: sneha.gupta != amit.kumar (different person)? YES
      d. Save approval (level=2)
      e. Advance: current_approval_level = 3, status = PENDING_L3
      f. Reset escalation_deadline = now + 48 hours
      g. Audit log: CSR_APPROVE_L2
      h. Notify: all ROLE_ADMIN users

  Step 4: LEVEL 3 — CA Manager Approves
  -------------------------------------------------------------------
    API:    POST /api/ra/requests/103/approve
    Auth:   admin (ROLE_ADMIN)
    Body:   { "comment": "Final approval granted" }

    System actions:
      a. Validate: current_approval_level == 3? YES
      b. Validate: admin has ROLE_ADMIN? YES
      c. Validate: admin != amit.kumar AND admin != sneha.gupta? YES
      d. Save approval (level=3)
      e. All levels complete --> status = FULLY_APPROVED
      f. Audit log: CSR_APPROVE_L3
      g. Send to CA --> issue certificate
      h. status = ISSUED

  REJECTION AT ANY LEVEL:
    If sneha.gupta rejects at Level 2:
      - status = REJECTED
      - Level 3 is SKIPPED (never reaches CA manager)
      - Requester notified: "Rejected at Level 2 by sneha.gupta: [reason]"
      - Audit log: CSR_REJECT_L2


  MODEL D — DELEGATION (Detailed Steps)
  =======================================================================

  Step 1: OPERATOR A CREATES DELEGATION
  -------------------------------------------------------------------
    API:    POST /api/ra/delegations
    Auth:   priya.patel (ROLE_ADMIN)
    Body:   {
              "delegateUsername": "vikram.singh",
              "validFrom": "2026-07-01T00:00:00Z",
              "validUntil": "2026-07-15T23:59:59Z"
            }

    System actions:
      a. Validate: vikram.singh exists and is_active? YES
      b. Validate: vikram.singh has same or higher role? YES
      c. Validate: valid_until > valid_from? YES
      d. Save delegation:
           approval_delegations (
             delegator_user_id = priya.patel.id,
             delegate_user_id = vikram.singh.id,
             valid_from = 2026-07-01, valid_until = 2026-07-15,
             is_active = true
           )
      e. Audit log: DELEGATION_CREATE
      f. Notify vikram.singh:
           "priya.patel has delegated approval authority to you
            from July 1 to July 15"

  Step 2: DURING DELEGATION — REQUEST ARRIVES
  -------------------------------------------------------------------
    Date: 2026-07-05 (within delegation period)
    CSR submitted --> status = PENDING

    Approver queue logic:
      a. Who can approve?

================================================================================
  12. ESCALATION & TIMEOUT RULES
================================================================================

  When an approval level is not completed within the configured time,
  the system automatically escalates or expires the request.

  ESCALATION FLOW:

    Request submitted --> PENDING (Level 1)
        |
        | escalation_hours = 48 (from policy)
        | escalation_deadline = submit_time + 48h
        |
        +-- 36 hours pass (75% of 48h) --> WARNING notification
        |   "Request #103 needs approval — escalation in 12 hours"
        |
        +-- 48 hours pass (100%) --> ESCALATION
            |
            | System actions:
            |   a. Current level's deadline passed
            |   b. Advance to NEXT level automatically
            |   c. Notify next-level approvers
            |   d. Audit log: CSR_ESCALATE
            |   e. Set new escalation_deadline for next level
            |
            | If NO more levels to escalate to:
            |   a. Status = EXPIRED_REQUEST
            |   b. Notify requester + all admins
            |   c. Audit log: CSR_EXPIRE
            |   d. Requester must re-submit

  QUARTZ JOB: ApprovalEscalationJob

    Runs every: 15 minutes
    Query:
      SELECT * FROM certificate_requests
      WHERE status LIKE 'PENDING%'
      AND escalation_deadline < NOW()

    For each expired request:
      - Check if next level exists in policy
      - YES: advance level + notify + new deadline
      - NO:  expire request + notify

  CONFIGURABLE TIMEOUTS (per policy):

    +-------------------------------+-----------+
    | Certificate Type              | Timeout   |
    +-------------------------------+-----------+
    | TLS Server (standard)         | 72 hours  |
    | TLS Client (internal)         | 48 hours  |
    | Code Signing (high-risk)      | 48 hours  |
    | Wildcard certificate          | 24 hours  |
    | Dev/test (auto-approve)       | N/A       |
    +-------------------------------+-----------+

================================================================================
  14. EDGE CASES & SECURITY CONSIDERATIONS
================================================================================

  14.1 — Race Conditions
  -------------------------------------------------------------------
    Problem:  Two operators approve same request simultaneously
    Solution: Optimistic locking on certificate_requests.status
              First approve wins, second gets 400 "not PENDING"
              Use @Version column or explicit status check in SQL:
                UPDATE certificate_requests
                SET status = 'APPROVED'
                WHERE id = :id AND status = 'PENDING'
              If rows_affected = 0 → someone else already changed it

  14.2 — Orphaned Requests
  -------------------------------------------------------------------
    Problem:  Request stuck in APPROVED but CA never responds
    Solution: Quartz job scans for status=APPROVED older than 1 hour
              Retry CA call or mark as FAILED
              Alert admin if retry also fails

  14.3 — Circular Delegation
  -------------------------------------------------------------------
    Problem:  A delegates to B, B delegates to C, C delegates to A
    Solution: No re-delegation allowed (TEST-D04)
              Only original authority holders can delegate

  14.4 — Privilege Escalation via Delegation
  -------------------------------------------------------------------
    Problem:  ROLE_VIEWER delegates to ROLE_ADMIN (escalation)
    Solution: Only delegate to same or higher role (TEST-D05)
              Delegation cannot GRANT new permissions

  14.5 — Time Zone Issues
  -------------------------------------------------------------------
    Problem:  Delegation valid_from/valid_until in different timezone
    Solution: All timestamps stored as UTC (DATETIME(6))
              Comparison always in UTC
              UI converts to local timezone for display only

  14.6 — Approval After Certificate Expiry
  -------------------------------------------------------------------
    Problem:  Request pending for months, cert validity would
              now exceed CA's expiry
    Solution: Re-validate Layer 6 (validity check) at approval time
              Not just at submission time

  14.7 — Bulk Approval
  -------------------------------------------------------------------
    Problem:  Admin wants to approve 50 requests at once
    Solution: POST /api/ra/requests/bulk-approve
              Body: { "requestIds": [101, 102, ...], "comment": "..." }
              Each request validated individually
              Partial success possible (some approved, some failed)
              Response includes per-request result

  14.8 — Audit Integrity
  -------------------------------------------------------------------
    Problem:  Admin tries to delete audit log entries
    Solution: audit_log has NO delete API
              No DELETE permission on table
              REQUIRES_NEW transaction (survives rollback)
              SIEM forwarding for off-site backup

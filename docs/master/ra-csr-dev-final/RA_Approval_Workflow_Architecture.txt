================================================================================
  1. OVERVIEW — MAKER-CHECKER MODEL
================================================================================

  This workflow uses a MAKER-CHECKER pattern:

  1. Client submits CSR → status = SUBMITTED
  2. ADMIN sees all requests → assigns to OPERATOR (Maker)
  3. MAKER reviews CSR → submits remarks → status = REVIEWED
  4. CHECKER (another operator) sees Maker's remarks →
     ACCEPTS or REJECTS → status = ACCEPTED / REJECTED
  5. ACCEPTED → sent to CA → ISSUED

  Rules:
    - Only ADMIN can see all CSR requests
    - Only ADMIN can assign a request to an operator
    - MAKER reviews and writes remarks (cannot accept/reject)
    - CHECKER sees Maker's remarks and accepts or rejects
    - The RA Operator who acts as the MAKER for a request is
      STRICTLY PROHIBITED from acting as the CHECKER for the
      same request. This is a mandatory separation of duties
      enforced at the application level. The system must reject
      any attempt by the Maker to accept or reject a request
      they have already reviewed.
    - Requester cannot be Maker or Checker

  2. ACTORS & ROLES
================================================================================

  +------------------+--------------------------------------------------+
  | Role             | Responsibilities                                 |
  +------------------+--------------------------------------------------+
  | CLIENT / USER    | Submits CSR (REST / EST / SCEP / CMP)            |
  |                  | Downloads issued certificate                     |
  +------------------+--------------------------------------------------+
  | ROLE_ADMIN       | Sees ALL submitted CSR requests                  |
  |                  | Assigns request to an Operator (Maker)           |
  |                  | Selects operator from dropdown                   |
  |                  | Can also act as Maker or Checker if needed       |
  +------------------+--------------------------------------------------+
  | ROLE_OPERATOR    | Acts as MAKER or CHECKER (not both on same req)  |
  | (Maker)          | Reviews CSR, writes remarks, submits review      |
  +------------------+--------------------------------------------------+
  | ROLE_OPERATOR    | Sees Maker's remarks                             |
  | (Checker)        | Accepts or Rejects the request                   |
  +------------------+--------------------------------------------------+
  | ROLE_AUDITOR     | Read-only access to all requests + audit logs    |
  +------------------+--------------------------------------------------+

  3. STATE MACHINE — REQUEST LIFECYCLE
================================================================================

  CSR Submitted
       |
       v
  [SUBMITTED] -----> Admin assigns to Operator (Maker)
       |
       v
  [ASSIGNED] ------> Maker reviews CSR
       |
       +----------------+--------------------+
       |                                     |
       v                                     v
  Maker recommends                     Maker returns to Admin
  (sends to Checker)                   (CSR has issues)
       |                                     |
       v                                     v
  [REVIEWED] ------> Checker         [RETURNED] -----> Admin sees
       |              sees remarks         |            returned request
       +----------+----------+             |
       |                     |             +--- Admin can:
       v                     |             |    1. Reassign to same/different Maker
  [ACCEPTED]                 |             |    2. Close the request permanently
       |                     |             |
       v                     |             v
  Send to CA                 |         [ASSIGNED] (reassign)
       |                     |              or
       +--------+            |         [CLOSED] (Admin closes permanently)
       |        |            |
       v        v            v
  [ISSUED]  [FAILED]    [REJECTED] -------> Goes back to Admin
       |                     |
       v                     +--- Admin sees rejected request
  [ACTIVE]                   |    Admin can:
                             |    1. Reassign to same/different Maker
                             |       (for re-review with new/updated CSR context)
                             |    2. Close the request permanently
                             |
                             v
                         [ASSIGNED] (reassign for re-review)
                              or
                         [CLOSED] (Admin closes permanently)


  STATE DEFINITIONS:

  +-----------------+---------------------------------------------------+
  | State           | Description                                       |
  +-----------------+---------------------------------------------------+
  | SUBMITTED       | CSR received, 7-layer validation passed,          |
  |                 | waiting for Admin to assign                       |
  +-----------------+---------------------------------------------------+
  | ASSIGNED        | Admin assigned to a Maker (operator),              |
  |                 | waiting for Maker to review                       |
  +-----------------+---------------------------------------------------+
  | RETURNED        | Maker returned the request to Admin with reason.   |
  |                 | Maker found issues during review and cannot        |
  |                 | recommend the request for approval.                |
  |                 | Admin can either:                                 |
  |                 |   a. Reassign to same or different operator        |
  |                 |   b. Reject the request directly                  |
  +-----------------+---------------------------------------------------+
  | REVIEWED        | Maker recommended and submitted review with        |
  |                 | remarks. Waiting for Checker to accept or reject. |
  +-----------------+---------------------------------------------------+
  | ACCEPTED        | Checker accepted, sending to CA for signing        |
  +-----------------+---------------------------------------------------+
  | REJECTED        | Checker rejected the request. NOT a final state.   |
  |                 | Request goes back to Admin's dashboard under        |
  |                 | ISSUES category. Admin can see the full trail:     |
  |                 |   - Who was the Maker (reviewed it)                |
  |                 |   - Who was the Checker (rejected it)              |
  |                 |   - Maker's remarks + Checker's rejection reason   |
  |                 | Admin can either:                                 |
  |                 |   a. Reassign to same or different operator        |
  |                 |      (for re-review — goes back to ASSIGNED)       |
  |                 |   b. Close the request permanently (→ CLOSED)      |
  +-----------------+---------------------------------------------------+
  | CLOSED          | Request permanently closed by Admin. This is the   |
  |                 | TRUE final state — no further action possible.     |
  |                 | Used when Admin decides the request should not     |
  |                 | proceed after reviewing Maker return reason or     |
  |                 | Checker rejection reason.                          |
  |                 | Requester notified with closure reason.            |
  +-----------------+---------------------------------------------------+
  | ISSUED          | CA signed successfully, certificate stored          |
  +-----------------+---------------------------------------------------+
  | FAILED          | CA signing failed (network/config error)           |
  |                 | Can be retried by Admin                           |
  +-----------------+---------------------------------------------------+

  VALID TRANSITIONS:

  +-------------------+---> +-------------------+--- Who ----------+
  | From              |     | To                |                   |
  +-------------------+     +-------------------+-------------------+
  | SUBMITTED         | --> | ASSIGNED          | Admin assigns     |
  | ASSIGNED          | --> | REVIEWED          | Maker recommends  |
  | ASSIGNED          | --> | RETURNED          | Maker returns     |
  | RETURNED          | --> | ASSIGNED          | Admin reassigns   |
  | RETURNED          | --> | CLOSED            | Admin closes      |
  | REVIEWED          | --> | ACCEPTED          | Checker accepts   |
  | REVIEWED          | --> | REJECTED          | Checker rejects   |
  | REJECTED          | --> | ASSIGNED          | Admin reassigns   |
  | REJECTED          | --> | CLOSED            | Admin closes      |
  | ACCEPTED          | --> | ISSUED            | CA signs OK       |
  | ACCEPTED          | --> | FAILED            | CA error          |
  | FAILED            | --> | ACCEPTED          | Admin retries     |
  +-------------------+     +-------------------+-------------------+

  IMPORTANT — REJECTED is NOT final:
    When Checker rejects, the request goes back to Admin.
    Admin decides whether to give it another chance (reassign)
    or permanently close it. Only CLOSED is the true final state.

  INVALID TRANSITIONS (blocked in code):

  | SUBMITTED → REVIEWED   | Cannot skip assignment              |
  | SUBMITTED → ACCEPTED   | Cannot skip Maker + Checker         |
  | ASSIGNED  → ACCEPTED   | Cannot skip Maker review            |
  | RETURNED  → REVIEWED   | Must be reassigned first            |
  | RETURNED  → ACCEPTED   | Must go through Maker again         |
  | CLOSED    → any        | True final state, no action possible|
  | ISSUED    → REJECTED   | Cannot un-issue (use revocation)    |

  STEP 3: ADMIN ASSIGNS REQUEST TO OPERATOR (MAKER)
  =================================================================
    API:    POST /api/ra/requests/{id}/assign
    Auth:   ROLE_ADMIN only
    Body:   { "operatorId": 5 }
            (operator selected from dropdown in UI)

    System:
      a. Validate: status == SUBMITTED
      b. Validate: operatorId exists, is_active, has ROLE_OPERATOR
      c. Validate: operator != requester
      d. Update: status = ASSIGNED,
                 assigned_to_id = 5,
                 assigned_at = now,
                 assigned_by_id = admin.id
      e. Audit: CSR_ASSIGN (resource=101, desc="Assigned to priya.patel")
      f. Notify: operator (Maker) — "CSR #101 assigned to you for review"

    Response: 200 OK
      { "id": 101, "status": "ASSIGNED",
        "assignedTo": "priya.patel", ... }

  STEP 6A: MAKER RECOMMENDS — SUBMITS REVIEW (happy path)
  =================================================================
    API:    POST /api/ra/requests/{id}/review
    Auth:   ROLE_OPERATOR (must be the assigned Maker)
    Body:   {
              "remarks": "CSR verified. Subject DN matches CMDB entry.
                          Key size 4096 meets policy. SANs valid.
                          Recommend approval."
            }

    System:
      a. Validate: status == ASSIGNED
      b. Validate: current user == assigned_to_id (only Maker can review)
      c. Update: status = REVIEWED,
                 maker_remarks = body.remarks,
                 maker_reviewed_at = now
      d. Audit: CSR_REVIEW (resource=101, desc="Maker reviewed with remarks")
      e. Notify: all ROLE_OPERATOR except Maker
         "CSR #101 reviewed by priya.patel — pending your acceptance"

    Response: 200 OK
      { "id": 101, "status": "REVIEWED",
        "makerRemarks": "CSR verified...",
        "makerUsername": "priya.patel",
        "makerReviewedAt": "2026-06-23T11:00:00Z" }


  STEP 6B: MAKER RETURNS REQUEST TO ADMIN (CSR has issues)
  =================================================================
    When the Maker finds issues during review and cannot recommend
    the request for approval, the Maker returns it to the Admin
    with a reason. The Maker does NOT have the authority to reject
    the request directly — only the Admin or Checker can reject.

    API:    POST /api/ra/requests/{id}/return
    Auth:   ROLE_OPERATOR (must be the assigned Maker)
    Body:   {
              "reason": "Subject DN contains unauthorized domain
                         evil.com which is not in the approved
                         domain list. CSR key size is only 1024
                         which does not meet minimum policy."
            }

    System:
      a. Validate: status == ASSIGNED
      b. Validate: current user == assigned_to_id (only Maker can return)
      c. Validate: reason is not blank
      d. Update: status = RETURNED,
                 maker_remarks = body.reason,
                 maker_reviewed_at = now
      e. Audit: CSR_RETURN (resource=101,
                desc="Maker returned to Admin: unauthorized domain")
      f. Notify: all ADMINs
         "CSR #101 returned by priya.patel: [reason]"

    Response: 200 OK
      { "id": 101, "status": "RETURNED",
        "makerRemarks": "Subject DN contains unauthorized domain...",
        "makerUsername": "priya.patel",
        "makerReviewedAt": "2026-06-23T11:00:00Z" }


  STEP 6C: ADMIN HANDLES RETURNED REQUEST
  =================================================================
    Admin sees the returned request in the ISSUES category of the
    dashboard. Admin reads the Maker's return reason and decides
    the next action.

    Admin has TWO options:

    OPTION 1 — REASSIGN to same or different operator:
    -----------------------------------------------------------------
    API:    POST /api/ra/requests/{id}/assign
    Auth:   ROLE_ADMIN
    Body:   { "operatorId": 7 }
            (same operator or a different one)

    System:
      a. Validate: status == RETURNED
      b. Same validation as original assignment
      c. Update: status = ASSIGNED,
                 assigned_to_id = 7 (new or same operator),
                 assigned_at = now,
                 assigned_by_id = admin.id
         Note: previous maker_remarks are preserved for history
      d. Audit: CSR_REASSIGN (resource=101,
                desc="Reassigned to vikram.singh after return")
      e. Notify: new Maker operator

    Use case:
      - Maker flagged a minor issue that requester can fix
      - Admin wants a second opinion from another operator
      - Same operator can review again after requester correction


    OPTION 2 — ADMIN CLOSES PERMANENTLY:
    -----------------------------------------------------------------
    API:    POST /api/ra/requests/{id}/close
    Auth:   ROLE_ADMIN
    Body:   {
              "reason": "Closed per Maker's findings.
                         Domain evil.com is permanently blocked."
            }

    System:
      a. Validate: status == RETURNED
      b. Update: status = CLOSED,
                 closed_at = now,
                 closed_by_id = admin.id,
                 closed_reason = body.reason
      c. Audit: CSR_CLOSED (resource=101,
                desc="Admin closed after Maker return: [reason]")
      d. Notify: requester + original Maker
         "CSR #101 permanently closed by Admin: [reason]"

    Use case:
      - Maker found a serious issue (blocked domain, weak key)
      - Admin agrees and closes without needing Checker review
      - CLOSED = true final state, no further action possible

  STEP 8A: CHECKER ACCEPTS
  =================================================================
    API:    POST /api/ra/requests/{id}/accept
    Auth:   ROLE_OPERATOR (must NOT be the Maker)
    Body:   { "remarks": "Agreed with Maker's assessment. Approved." }

    CRITICAL VALIDATION — SEPARATION OF DUTIES:
      The RA Operator who acted as the Maker (reviewed this request
      and submitted remarks) is strictly prohibited from acting as
      the Checker. The system compares the current user's ID against
      the assigned_to_id field. If they match, the request is
      rejected with HTTP 403 (PKI_APR_005: "The operator who
      reviewed this request cannot accept or reject it. A different
      operator must perform the Checker role.").

    System:
      a. Validate: status == REVIEWED
      b. Validate: current user != assigned_to_id (Checker != Maker)
         → FAIL: 403 PKI_APR_005 — separation of duties violation
      c. Validate: current user != requester
      d. Update: status = ACCEPTED,
                 checker_id = current_user.id,
                 checker_decision = ACCEPTED,
                 checker_remarks = body.remarks,
                 checker_decided_at = now
      e. Audit: CSR_ACCEPT (resource=101)
      f. AUTO-ISSUE: send CSR to CA
           --> CaClient.sign(csrPem, validityDays, sans)
           --> Save certificate, update status = ISSUED
      g. Audit: CERT_ISSUE
      h. Notify: requester "Your certificate has been issued"

    Response: 200 OK
      { "id": 101, "status": "ISSUED",
        "certificateSerial": "4F2A1B3C...",
        "checkerUsername": "vikram.singh",
        "checkerRemarks": "Agreed with Maker's assessment..." }


  STEP 8B: CHECKER REJECTS
  =================================================================
    API:    POST /api/ra/requests/{id}/reject
    Auth:   ROLE_OPERATOR (must NOT be the Maker)
    Body:   { "remarks": "Domain not in approved list. Rejecting." }

    CRITICAL VALIDATION — SEPARATION OF DUTIES:
      Same rule as accept — the Maker operator cannot reject the
      request either. A different operator must perform this action.

    System:
      a. Validate: status == REVIEWED
      b. Validate: current user != assigned_to_id (Checker != Maker)
         → FAIL: 403 PKI_APR_005 — separation of duties violation
      c. Update: status = REJECTED,
                 checker_id = current_user.id,
                 checker_decision = REJECTED,
                 checker_remarks = body.remarks,
                 checker_decided_at = now,
                 status_reason = body.remarks
      d. Audit: CSR_REJECT (resource=101)
      e. Notify: ALL ADMINs + Maker
         "CSR #101 rejected by vikram.singh: Domain not in approved list"
         → Request appears in Admin's ISSUES → REJECTED section

    Response: 200 OK
      { "id": 101, "status": "REJECTED",
        "checkerUsername": "vikram.singh",
        "checkerRemarks": "Domain not in approved list..." }

    WHAT HAPPENS NEXT — REJECTED goes to Admin dashboard:
      Admin sees rejected request in ISSUES category.
      Admin sees full trail: Maker remarks + Checker rejection reason.
      Admin has TWO options:
        1. Reassign: POST /api/ra/requests/101/assign
           → status = ASSIGNED (Maker reviews again with new context)
        2. Close permanently: POST /api/ra/requests/101/close
           → status = CLOSED (true final state, no further action)


  STEP 9: ADMIN HANDLES REJECTED REQUEST
  =================================================================

    OPTION 1 — REASSIGN (give it another chance):
    -----------------------------------------------------------------
    API:    POST /api/ra/requests/{id}/assign
    Auth:   ROLE_ADMIN
    Body:   { "operatorId": 9 }

    System:
      a. Validate: status == REJECTED
      b. Update: status = ASSIGNED (back into pipeline)
      c. Previous Maker/Checker remarks preserved for history
      d. Audit: CSR_REASSIGN_AFTER_REJECT
      e. Notify: new Maker operator

    Use case:
      - Checker rejected but Admin thinks issue is fixable
      - Requester has provided additional context
      - Admin wants a different operator to review fresh

    OPTION 2 — CLOSE PERMANENTLY:
    -----------------------------------------------------------------
    API:    POST /api/ra/requests/{id}/close
    Auth:   ROLE_ADMIN
    Body:   { "reason": "Confirmed: domain is permanently blocked.
                         Request cannot be fulfilled." }

    System:
      a. Validate: status == REJECTED or RETURNED
      b. Update: status = CLOSED,
                 closed_at = now,
                 closed_by_id = admin.id,
                 closed_reason = body.reason
      c. Audit: CSR_CLOSED (resource=101)
      d. Notify: requester + Maker
         "CSR #101 permanently closed by Admin: [reason]"

    CLOSED is the TRUE FINAL STATE — no further action possible.

  KEY RULES:
    1. The RA Operator who performed the Maker role (reviewed the
       request and submitted remarks) is STRICTLY PROHIBITED from
       acting as the Checker for the same request. This is the
       fundamental separation of duties principle — no single
       operator can both review and approve/reject a certificate
       request. The system enforces this at the API level by
       comparing the current user's ID against the assigned_to_id
       (Maker) before allowing accept or reject operations. Any
       violation returns HTTP 403 with error PKI_APR_005.
    2. Requester cannot be Maker or Checker
    3. Only Admin can assign (select from operator dropdown)
    4. Only assigned Maker can submit review
    5. Any operator EXCEPT the Maker can be Checker

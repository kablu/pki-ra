================================================================================
  ABSTRACT
================================================================================

  This document describes the approval workflow architecture for the Enterprise
  Registration Authority (RA) system. It covers the configurable Maker-Checker
  model, database schema, REST API design, state machine, workflow
  configuration, and CA integration lifecycle for CSR approval and certificate
  issuance.

  SCOPE NOTE -- CSR Request Payload and Validation  [CHANGED v1 -- C-01]

  The CSR submission request payload (field definitions, PKCS#10 vs CRMF
  format support, subjectAltName cross-verification rules, requestor data
  handling, and additionalAttributes schema validation) are OUT OF SCOPE for
  this document.

  A separate document -- RA_CSR_Request_Payload_and_Validation.md -- will be
  provided to cover those topics in detail.

  This document focuses exclusively on the approval workflow that begins after
  a CSR has been received, validated, and placed in SUBMITTED status.

================================================================================
  1.  OVERVIEW AND ENTRY POINT
================================================================================

  The RA approval workflow starts AFTER a CSR request has been received and
  validated by the validation engine. Requests that fail validation never enter
  the approval pipeline. The workflow operates only on requests in SUBMITTED
  status.

  The approval process is fully configurable per certificate profile. An
  administrator defines one or more workflow configurations (e.g., DUAL mode
  with Self-Pickup, SINGLE mode with Self-Pickup) and maps each certificate
  profile to a configuration. When a request arrives, the system resolves the
  workflow configuration from the request's profile and applies it
  automatically.

  1.1  Entry Condition
  --------------------

    CSR received by RA
          |
          v
    Validation Engine runs
          |
          +---[PASS]---> status = SUBMITTED  <-- Approval workflow starts here
          |
          +---[FAIL]---> status = VALIDATION_FAILED  (does not enter workflow)

  1.2  Workflow Model
  -------------------

  The system supports two approval modes:

  SINGLE  --  One operator reviews, verifies, and approves or rejects the
              request. No second operator is needed.

  DUAL    --  Two operators are required. The Maker reviews the request and
              submits remarks. A different operator (Checker) then makes the
              final approval or rejection decision. Separation of duties is
              enforced at the API level.

  The assignment strategy (how requests reach operators) is also configurable
  per workflow configuration:

  Self-Pickup   --  Operators pick requests from a shared pool.
  Admin-Assign  --  Admin manually assigns each request to a specific operator.


================================================================================
  2.  PRE-APPROVAL STATUS FLOW
================================================================================

  These statuses are managed by the system automatically before the workflow
  begins. They are listed here for completeness.

    [RECEIVED]
        |
        v
    Validation
        |
        +---[PASS]---> [VALIDATED] ---> [SUBMITTED]  <-- workflow starts
        |
        +---[FAIL]---> [VALIDATION_FAILED]  (terminal for this submission)

  Status              Set By   Description
  ------------------  -------  -------------------------------------------------
  RECEIVED            System   CSR received and saved. Validation not started.
  VALIDATED           System   Validation passed. Transitions immediately
                               to SUBMITTED.
  VALIDATION_FAILED   System   One or more validation layers failed. Request
                               does not enter approval. Client must fix and
                               resubmit.
  SUBMITTED           System   Validation passed. Request is in the approval
                               pool. Available for operator pickup or admin
                               assignment.

  NOTE: The approval workflow (Maker-Checker process) operates exclusively on
  requests that have reached SUBMITTED status.


================================================================================
  3.  ACTORS AND ROLES
================================================================================

  Role              Responsibilities
  ----------------  -------------------------------------------------------------
  CLIENT / USER     Submits CSR. Polls for status. Downloads issued certificate.

  ROLE_ADMIN        Defines workflow configurations. Maps profiles to
                    configurations. Monitors all records. Assigns requests to
                    operators. Closes requests permanently. Retries failed
                    CA calls.

  ROLE_OPERATOR     In SINGLE mode: picks up request, reviews, and approves or
                    rejects directly.
                    In DUAL mode as Maker: picks up and submits review remarks.
                    In DUAL mode as Checker: picks up reviewed request and makes
                    final decision.
                    Operator cannot be both Maker and Checker for the same
                    request.

  ROLE_AUDITOR      Read-only access to all requests, transition history,
                    and audit logs.


================================================================================
  4.  WORKFLOW CONFIGURATION -- PER-PROFILE MODEL       [CHANGED v1 -- C-13]
================================================================================

  NOTE: This section replaces the previous single system-wide configuration
  design. In V0.1, there was one global approval_mode setting that applied to
  all requests regardless of certificate profile. Sebastian's feedback
  identified this as a significant design constraint -- different profiles
  carry different risk levels and must be able to follow different approval
  workflows independently.

  4.1  Design
  -----------

  The Admin defines one or more Workflow Configurations. Each configuration
  specifies the approval mode, assignment strategy, and operational settings.
  Each Certificate Profile (TLS_SERVER, CODE_SIGNING, SMIME, etc.) is then
  mapped to exactly one workflow configuration.

  When a request arrives, the system resolves the profile, looks up the mapped
  workflow configuration, and applies it for the entire lifecycle of that
  request.

    Request arrives with csrProfile = "TLS_SERVER"
            |
            v
    Lookup: csr_profiles --> profile_id = 1 ("TLS_SERVER")
            |
            v
    Lookup: profile_workflow_mapping --> workflow_config_id = 1
            |
            v
    Lookup: workflow_configurations --> id = 1
            approval_mode   = DUAL
            assignment_mode = SELF_PICKUP
            require_remarks = true
            max_pending     = 10
            |
            v
    Apply this configuration for this request's full lifecycle

  4.2  Database Tables
  --------------------

  Table: workflow_configurations

  Stores named, reusable workflow configuration objects.

  Column                    Type           Null  Description
  ------------------------  -------------  ----  ------------------------------
  id                        BIGINT PK      NO    Auto-increment primary key
  name                      VARCHAR(100)   NO    Human-readable name
                                                 e.g. "High Security DUAL"
  approval_mode             VARCHAR(10)    NO    SINGLE or DUAL
  assignment_mode           VARCHAR(20)    NO    SELF_PICKUP or ADMIN_ASSIGN
  require_remarks           BOOLEAN        NO    Whether operator remarks are
                                                 mandatory
  max_pending_per_operator  INT            NO    Max requests one operator can
                                                 hold at a time
  maker_can_return          BOOLEAN        NO    Whether Maker is allowed to
                                                 return a request to Admin
  is_active                 BOOLEAN        NO    Inactive configs cannot be
                                                 used for new mappings
  created_at                DATETIME(6)    NO    When this config was created
  created_by                VARCHAR(100)   NO    Admin who created it

  ----

  Table: csr_profiles  [CHANGED v1 -- C-03]

  Replaces the previous csr_profile VARCHAR(50) column in csr_requests.
  Profiles are now first-class entities.

  Column       Type           Null  Description
  -----------  -------------  ----  ------------------------------------------
  id           BIGINT PK      NO    Auto-increment primary key
  name         VARCHAR(50)    NO    Profile code: TLS_SERVER, TLS_CLIENT,
                                    CODE_SIGNING, SMIME, DOCUMENT_SIGNING
  description  VARCHAR(500)   YES   Human-readable description
  is_active    BOOLEAN        NO    Whether new requests can use this profile
  created_at   DATETIME(6)    NO    Creation time

  ----

  Table: profile_workflow_mapping

  Binds each certificate profile to exactly one workflow configuration.
  This is what the system uses at request time to determine how to process
  the request.

  Column              Type           Null  Description
  ------------------  -------------  ----  ------------------------------------
  id                  BIGINT PK      NO    Auto-increment primary key
  profile_id          BIGINT FK      NO    --> csr_profiles.id
  workflow_config_id  BIGINT FK      NO    --> workflow_configurations.id
  effective_from      DATETIME(6)    NO    When this mapping takes effect
  effective_until     DATETIME(6)    YES   NULL = currently active
  created_by          VARCHAR(100)   NO    Admin who created the mapping
  created_at          DATETIME(6)    NO    When mapping was created

  NOTE: Only one mapping per profile may be active at a time
  (i.e., effective_until IS NULL). Admin creates a new mapping to override --
  the old one is closed with effective_until = now.

  4.3  Example Configuration Setup
  ---------------------------------

  Workflow Configuration 1 -- "High Security DUAL Self-Pickup"

    id              = 1
    name            = "High Security DUAL Self-Pickup"
    approval_mode   = DUAL
    assignment_mode = SELF_PICKUP
    require_remarks = true
    max_pending     = 5
    maker_can_return= true

  Mapped profiles: TLS_SERVER, CODE_SIGNING

  Rationale: These profiles issue certificates for public-facing servers and
  code signing. Two-operator review reduces the risk of a misconfigured or
  fraudulent certificate being issued.

  ----

  Workflow Configuration 2 -- "Standard SINGLE Self-Pickup"

    id              = 2
    name            = "Standard SINGLE Self-Pickup"
    approval_mode   = SINGLE
    assignment_mode = SELF_PICKUP
    require_remarks = true
    max_pending     = 10
    maker_can_return= true

  Mapped profiles: TLS_CLIENT, SMIME, DOCUMENT_SIGNING

  Rationale: These profiles are lower risk and internal. A single-operator
  review is sufficient.

  4.4  Admin API for Configuration Management
  --------------------------------------------

  # Workflow Configurations
  POST   /api/ra/admin/workflow-configs          Create a new workflow config
  GET    /api/ra/admin/workflow-configs          List all workflow configs
  GET    /api/ra/admin/workflow-configs/{id}     Get a specific config
  PUT    /api/ra/admin/workflow-configs/{id}     Update a config

  # Profile-to-Config Mappings
  POST   /api/ra/admin/profile-mappings          Map a profile to a config
  GET    /api/ra/admin/profile-mappings          List all active mappings
  PUT    /api/ra/admin/profile-mappings/{id}     Update a mapping

  All endpoints: Auth ROLE_ADMIN only.

  Example -- Create Workflow Configuration:

    POST /api/ra/admin/workflow-configs
    Authorization: Bearer <admin-token>
    Content-Type: application/json

    {
      "name": "High Security DUAL Self-Pickup",
      "approvalMode": "DUAL",
      "assignmentMode": "SELF_PICKUP",
      "requireRemarks": true,
      "maxPendingPerOperator": 5,
      "makerCanReturn": true
    }

    Response 201 Created:
    {
      "id": 1,
      "name": "High Security DUAL Self-Pickup",
      "approvalMode": "DUAL",
      "assignmentMode": "SELF_PICKUP",
      "requireRemarks": true,
      "maxPendingPerOperator": 5,
      "isActive": true
    }

  Example -- Map Profile to Configuration:

    POST /api/ra/admin/profile-mappings
    Authorization: Bearer <admin-token>
    Content-Type: application/json

    {
      "profileId": 1,
      "workflowConfigId": 1
    }

    Response 201 Created:
    {
      "profileName": "TLS_SERVER",
      "workflowConfigName": "High Security DUAL Self-Pickup",
      "effectiveFrom": "2026-06-30T00:00:00Z"
    }

  4.5  Runtime Resolution
  -----------------------

  At the time an operator picks up a request, the system:

    1. Reads csr_requests.profile_id
    2. Queries profile_workflow_mapping for the active mapping
    3. Loads the associated workflow_configurations row
    4. Stores workflow_config_id and approval_mode on the request record
       (approval_mode_at_pickup)
    5. Applies that configuration for the entire lifecycle of this request --
       even if the mapping is later changed for future requests

  This ensures a request never changes its approval rules mid-flow.


================================================================================
  5.  STATE MACHINE
================================================================================

  5.1  SINGLE Mode
  ----------------

    [SUBMITTED]
         |
         | Operator picks up (Self-Pickup) or Admin assigns
         v
    [IN_REVIEW]   <-- Operator reviewing
         |
         +---[approve]---> [APPROVED] ---> [SENT_TO_CA] ---> [ISSUED]
         |                                              ----> [PENDING] --> [ISSUED] / [FAILED]
         |                                              ----> [FAILED]
         +---[reject]----> [REJECTED] ---> Admin (reassign or close)
         |
         +---[return]----> [RETURNED] ---> Admin (reassign or close)

  5.2  DUAL Mode
  --------------

    [SUBMITTED]
         |
         | Maker picks up (Self-Pickup) or Admin assigns as Maker
         v
    [IN_REVIEW]   <-- Maker reviewing
         |
         +---[review]----> [REVIEWED]   <-- Waiting for Checker
         |                      |
         |                      | Checker picks up (must not be Maker)
         |                      v
         |                 [Checker reviewing]
         |                      |
         |                      +---[approve]--> [APPROVED] ---> [SENT_TO_CA]
         |                      |                               ----> [ISSUED]
         |                      |                               ----> [PENDING] --> [ISSUED] / [FAILED]
         |                      |                               ----> [FAILED]
         |                      +---[reject]---> [REJECTED] ---> Admin
         |
         +---[return]----> [RETURNED] ---> Admin (reassign or close)

  5.3  State Definitions
  ----------------------

  State          Description
  -------------  --------------------------------------------------------------
  SUBMITTED      Validation passed. Visible to all operators and Admin.
                 Available for pickup or assignment.

  IN_REVIEW      An operator has picked up the request.
                 SINGLE mode: this operator will approve or reject.
                 DUAL mode: this is the Maker.

  REVIEWED       DUAL mode only. Maker submitted remarks. Waiting for a
                 different operator to act as Checker.

  RETURNED       Operator sent request back to Admin -- needs clarification
                 or reassignment.

  APPROVED       Approved by single operator (SINGLE) or Checker (DUAL).
                 Request dispatched to CA.

  REJECTED       Rejected by operator or Checker. Goes to Admin for
                 reassignment or closure.

  CLOSED         Permanently closed by Admin. No further action possible.

  SENT_TO_CA     [CHANGED v1 -- C-14]
                 Request has been dispatched to the CA. Awaiting response.

  PENDING        [CHANGED v1 -- C-14]
                 CA acknowledged the request but has not yet issued the
                 certificate (async CA processing).

  ISSUED         CA signed the certificate successfully. Certificate active.

  FAILED         CA signing failed. Admin can review and retry.

  5.4  Valid Transitions
  ----------------------

  From           To             Who / When
  -------------  -------------  -----------------------------------------------
  SUBMITTED      IN_REVIEW      Operator self-pickup or Admin assigns
  IN_REVIEW      APPROVED       SINGLE mode: operator approves directly
  IN_REVIEW      REJECTED       SINGLE mode: operator rejects directly
  IN_REVIEW      REVIEWED       DUAL mode: Maker submits remarks
  IN_REVIEW      RETURNED       Operator returns to Admin (any mode)
  REVIEWED       APPROVED       DUAL mode: Checker approves
  REVIEWED       REJECTED       DUAL mode: Checker rejects
  RETURNED       IN_REVIEW      Admin reassigns to another operator
  RETURNED       CLOSED         Admin permanently closes
  REJECTED       IN_REVIEW      Admin reassigns
  REJECTED       CLOSED         Admin permanently closes
  APPROVED       SENT_TO_CA     System dispatches to CA [CHANGED v1 -- C-14]
  SENT_TO_CA     ISSUED         CA responded synchronously with certificate
  SENT_TO_CA     PENDING        CA acknowledged, processing async [C-14]
  SENT_TO_CA     FAILED         CA returned an error
  PENDING        ISSUED         CA callback received with certificate [C-14]
  PENDING        FAILED         CA callback received with failure [C-14]
  FAILED         SENT_TO_CA     Admin retries


================================================================================
  6.  DETAILED FLOW -- SINGLE MODE WITH SELF-PICKUP     [CHANGED v1 -- C-15]
================================================================================

  This flow applies when a certificate profile (e.g., TLS_CLIENT, SMIME) is
  mapped to a workflow configuration with approval_mode = SINGLE and
  assignment_mode = SELF_PICKUP.

  One operator picks the request from the shared pool and is solely responsible
  for reviewing and deciding.

  Step 1 -- Client Submits CSR
  ----------------------------

    POST /api/ra/requests
    Auth: Any authenticated user or system

  The system receives the request, runs the validation, and if all checks pass,
  places the request in SUBMITTED status.

  System resolves the workflow configuration:
    Profile = TLS_CLIENT --> mapped to workflow config: SINGLE Self-Pickup
    approval_mode_at_pickup = SINGLE stored when operator picks up

  Response to client:
    {
      "requestId": "RA-REQ-2026-00000042",
      "status": "SUBMITTED",
      "message": "Validation passed. Request is in the approval queue."
    }

  The request is now visible in the shared operator pool.

  Step 2 -- Operator Views the Pool
  ----------------------------------

    GET /api/ra/requests/pool
    Auth: ROLE_OPERATOR

  Returns all requests in SUBMITTED status that are unclaimed.

  Response example:
    [
      {
        "requestId": "RA-REQ-2026-00000042",
        "subjectDn": "CN=client.acme.com, O=Acme Corp, C=IN",
        "csrProfile": "TLS_CLIENT",
        "priority": "NORMAL",
        "status": "SUBMITTED",
        "submittedAt": "2026-06-30T10:00:00Z",
        "workflowMode": "SINGLE"
      }
    ]

  Step 3 -- Operator Picks Up the Request
  ----------------------------------------

    POST /api/ra/requests/{requestId}/pickup
    Auth: ROLE_OPERATOR

  Server-side checks before pickup:
    - Request must be in SUBMITTED status
    - Operator must not be the original requestor
    - Operator must not exceed max_pending_per_operator

  On success:
    - status             --> IN_REVIEW
    - maker_id           --> current operator's user ID
    - assigned_at        --> current timestamp
    - approval_mode_at_pickup --> SINGLE
    - Transition history entry created

  All other operators now see this request as IN_REVIEW. They cannot pick it up.

  Response:
    {
      "requestId": "RA-REQ-2026-00000042",
      "status": "IN_REVIEW",
      "pickedUpBy": "priya.patel",
      "pickedUpAt": "2026-06-30T10:15:00Z",
      "workflowMode": "SINGLE",
      "message": "Request is now assigned to you. Review and approve or reject."
    }

  Step 4a -- Operator Approves
  -----------------------------

    POST /api/ra/requests/{requestId}/approve
    Auth: ROLE_OPERATOR
    Content-Type: application/json

    {
      "remarks": "CSR verified. Subject DN matches registered domain.
                  Key size 4096 RSA. Approved."
    }

  Server-side checks:
    - Caller must be the operator who picked up (maker_id == currentUser.id)
    - approval_mode_at_pickup must be SINGLE
    - Remarks required if require_remarks = true in workflow config

  On success:
    - status             --> APPROVED
    - maker_remarks      --> saved
    - maker_reviewed_at  --> current timestamp
    - System dispatches to CA --> status --> SENT_TO_CA

  Response:
    {
      "requestId": "RA-REQ-2026-00000042",
      "status": "SENT_TO_CA",
      "message": "Request approved and dispatched to CA for signing."
    }

  Flow continues at Step 6 (CA issuance).

  Step 4b -- Operator Rejects
  ----------------------------

    POST /api/ra/requests/{requestId}/approve
    Auth: ROLE_OPERATOR
    Content-Type: application/json

    {
      "decision": "REJECT",
      "remarks": "Subject DN does not match the registered domain. Resubmit."
    }

  NOTE: The same /approve endpoint handles both approve and reject decisions.
  The server routes based on the "decision" field.  [CHANGED v1 -- C-11]

  On success:
    - status         --> REJECTED
    - maker_remarks  --> saved
    - Request appears in Admin dashboard under the REJECTED bucket

  Admin then either:
    - Reassigns to a different operator --> status back to IN_REVIEW
    - Closes the request permanently --> status --> CLOSED

  Step 4c -- Operator Returns to Admin
  -------------------------------------

    POST /api/ra/requests/{requestId}/return
    Auth: ROLE_OPERATOR
    Content-Type: application/json

    {
      "reason": "Requestor's domain is not in the approved domain list.
                 Needs Admin verification before I can approve."
    }

  On success:
    - status    --> RETURNED
    - maker_id  remains (audit trail)

  Admin options:
    - Reassign to same or different operator --> status back to IN_REVIEW
    - Close permanently --> status --> CLOSED

  Step 5 -- Admin Actions on REJECTED or RETURNED
  -------------------------------------------------

    # Reassign to a different operator
    POST /api/ra/requests/{requestId}/assign
    Auth: ROLE_ADMIN

    {
      "operatorId": 7,
      "remarks": "Reassigned -- previous operator unavailable."
    }

    On success:
      - status      --> IN_REVIEW
      - maker_id    --> new operator ID
      - assigned_at --> current timestamp
      - Transition history entry created

    # Or permanently close
    POST /api/ra/requests/{requestId}/close
    Auth: ROLE_ADMIN

    {
      "reason": "Request withdrawn by requestor."
    }

    On success:
      - status        --> CLOSED
      - closed_by_id  --> Admin user ID
      - closed_at     --> current timestamp
      - closed_reason --> saved
      - No further actions possible on this request

  Step 6 -- CA Issuance (SINGLE and DUAL, all paths)
  ---------------------------------------------------

  See Section 12 for full detail. The possible outcomes after SENT_TO_CA are:

    [SENT_TO_CA]
         |
         +---> [ISSUED]   CA responded synchronously with a signed certificate
         |
         +---> [PENDING]  CA acknowledged but is processing asynchronously
         |          |
         |          +---> [ISSUED]   CA callback arrives with certificate
         |          +---> [FAILED]   CA callback arrives with error
         |
         +---> [FAILED]   CA returned an error immediately
                     |
                     +---> Admin retries --> back to [SENT_TO_CA]
                     +---> Admin closes  --> [CLOSED]

  Complete SINGLE Self-Pickup -- Status Lifecycle Summary
  -------------------------------------------------------

    SUBMITTED
      --> IN_REVIEW            (operator self-pickup)
            --> APPROVED       (operator approves)
                --> SENT_TO_CA (system dispatches to CA)
                    --> ISSUED
                    --> PENDING --> ISSUED / FAILED
                    --> FAILED  --> Admin retries --> SENT_TO_CA
            --> REJECTED       (operator rejects)
                --> IN_REVIEW  (Admin reassigns)
                --> CLOSED     (Admin closes)
            --> RETURNED       (operator returns)
                --> IN_REVIEW  (Admin reassigns)
                --> CLOSED     (Admin closes)


================================================================================
  7.  DETAILED FLOW -- DUAL MODE WITH SELF-PICKUP       [CHANGED v1 -- C-15]
================================================================================

  This flow applies when a certificate profile (e.g., TLS_SERVER, CODE_SIGNING)
  is mapped to a workflow configuration with approval_mode = DUAL and
  assignment_mode = SELF_PICKUP.

  Two operators are required. The Maker reviews the request first and submits a
  recommendation. A different operator (the Checker) then makes the final
  approval or rejection decision. The same person cannot be both Maker and
  Checker for the same request -- separation of duties enforced at the API level.

  Step 1 -- Client Submits CSR
  ----------------------------

  Same as SINGLE mode Step 1. On successful validation:
    - status --> SUBMITTED
    - Workflow config resolved: DUAL Self-Pickup
    - Request visible in shared pool to all operators

  Response to client:
    {
      "requestId": "RA-REQ-2026-00000043",
      "status": "SUBMITTED",
      "message": "Validation passed. Request is in the approval queue.",
      "workflowMode": "DUAL"
    }

  Step 2 -- Maker Views the Pool
  --------------------------------

    GET /api/ra/requests/pool
    Auth: ROLE_OPERATOR

  Returns requests in SUBMITTED status. Response includes workflowMode: DUAL
  so the operator knows a second operator will be required after review.

  Step 3 -- Maker Picks Up the Request
  --------------------------------------

    POST /api/ra/requests/{requestId}/pickup
    Auth: ROLE_OPERATOR

  Server-side checks:
    - Request must be in SUBMITTED status
    - Operator must not be the original requestor
    - Operator must not exceed max pending limit

  On success:
    - status                   --> IN_REVIEW
    - maker_id                 --> current operator's user ID
    - assigned_at              --> current timestamp
    - approval_mode_at_pickup  --> DUAL
    - Transition history entry created

  Response:
    {
      "requestId": "RA-REQ-2026-00000043",
      "status": "IN_REVIEW",
      "yourRole": "MAKER",
      "pickedUpBy": "priya.patel",
      "pickedUpAt": "2026-06-30T10:15:00Z",
      "workflowMode": "DUAL",
      "message": "You are the Maker. Review the request and submit your
                  remarks. A Checker will make the final decision."
    }

  Step 4 -- Maker Reviews and Submits Remarks
  --------------------------------------------

  The Maker carefully reviews:
    - Subject DN correctness
    - SAN entries (if present)
    - Key algorithm and key size against profile policy
    - Validity period against profile constraints
    - Requestor identity and purpose
    - Validation flags and warnings

  The Maker does NOT make the final approval decision -- they submit a
  recommendation with remarks.

    POST /api/ra/requests/{requestId}/review
    Auth: ROLE_OPERATOR
    Content-Type: application/json

    {
      "remarks": "CSR reviewed. Subject DN CN=api.acme.com matches registered
                  domain. RSA-4096 key meets policy. SAN dns:api.acme.com
                  verified. No validation flags. Recommend approval."
    }

  Server-side checks:
    - Caller must be the Maker (maker_id == currentUser.id)
    - approval_mode_at_pickup must be DUAL
    - Remarks required if require_remarks = true

  On success:
    - status            --> REVIEWED
    - maker_remarks     --> saved
    - maker_reviewed_at --> current timestamp
    - Transition history entry created

  The request now appears in the Checker pool -- visible to all operators
  EXCEPT the Maker. This ensures the Checker is always a different person.

  Response:
    {
      "requestId": "RA-REQ-2026-00000043",
      "status": "REVIEWED",
      "message": "Your review has been submitted. Request is now awaiting
                  Checker decision."
    }

  Step 4 (alternate) -- Maker Returns to Admin
  ---------------------------------------------

    POST /api/ra/requests/{requestId}/return
    Auth: ROLE_OPERATOR

    {
      "reason": "Domain api-legacy.acme.com is flagged as decommissioned.
                 Needs Admin verification before Maker can recommend."
    }

  On success:
    - status    --> RETURNED
    - maker_id  remains for audit trail
    - Request appears in Admin dashboard RETURNED bucket

  Admin can reassign to a different Maker or close permanently.

  Step 5 -- Checker Views the Checker Pool
  -----------------------------------------

    GET /api/ra/requests/pool?forChecker=true
    Auth: ROLE_OPERATOR

  Returns all requests in REVIEWED status where maker_id != currentUser.id.

  The Checker can see:
    - The request details (CSR, subject DN, profile, validity)
    - The Maker's remarks and recommendation
    - The Maker's name
    - Validation results

  Response example:
    [
      {
        "requestId": "RA-REQ-2026-00000043",
        "subjectDn": "CN=api.acme.com, O=Acme Corp, C=IN",
        "csrProfile": "TLS_SERVER",
        "status": "REVIEWED",
        "makerName": "priya.patel",
        "makerRemarks": "CSR reviewed. RSA-4096. Recommend approval.",
        "makerReviewedAt": "2026-06-30T10:45:00Z",
        "workflowMode": "DUAL"
      }
    ]

  Step 6 -- Checker Picks Up the Reviewed Request
  -------------------------------------------------

    POST /api/ra/requests/{requestId}/pickup
    Auth: ROLE_OPERATOR

  Server-side checks:
    - Request must be in REVIEWED status
    - Caller MUST NOT be the Maker (maker_id != currentUser.id)
      Separation of duties enforced.
    - If violation: 403 PKI_APR_005

  On success:
    - checker_id --> current operator's user ID
    - No status change -- request stays in REVIEWED
    - Transition history entry: "Checker picked up"

  Response:
    {
      "requestId": "RA-REQ-2026-00000043",
      "status": "REVIEWED",
      "yourRole": "CHECKER",
      "checkerPickedUpBy": "vikram.singh",
      "makerName": "priya.patel",
      "makerRemarks": "CSR reviewed. RSA-4096. Recommend approval.",
      "message": "You are the Checker. Review the Maker's remarks and the
                  request, then approve or reject."
    }

  Step 7a -- Checker Approves
  ----------------------------

    POST /api/ra/requests/{requestId}/approve
    Auth: ROLE_OPERATOR
    Content-Type: application/json

    {
      "remarks": "Agreed with Maker's assessment. Domain verified.Approving."
    }

  Server-side routing  [CHANGED v1 -- C-11]:
    - Server checks checker_id == currentUser.id
    - approval_mode_at_pickup == DUAL
    - Routes this as a Checker approval decision

  On success:
    - status            --> APPROVED
    - checker_decision  --> APPROVED
    - checker_remarks   --> saved
    - checker_decided_at --> current timestamp
    - System dispatches to CA --> status --> SENT_TO_CA

  Response:
    {
      "requestId": "RA-REQ-2026-00000043",
      "status": "SENT_TO_CA",
      "message": "Request approved by Checker and dispatched to CA."
    }

  Step 7b -- Checker Rejects
  ---------------------------

    POST /api/ra/requests/{requestId}/approve
    Auth: ROLE_OPERATOR
    Content-Type: application/json

    {
      "decision": "REJECT",
      "remarks": "Domain api.acme.com is scheduled for retirement next month.
                  Certificate issuance at this time is not appropriate."
    }

  On success:
    - status             --> REJECTED
    - checker_decision   --> REJECTED
    - checker_remarks    --> saved
    - checker_decided_at --> current timestamp
    - Request appears in Admin dashboard REJECTED bucket

  Step 8 -- CA Issuance
  ----------------------

  Same as SINGLE mode Step 6. See Section 12 for full detail.

  Complete DUAL Self-Pickup -- Status Lifecycle Summary
  ------------------------------------------------------

    SUBMITTED
      --> IN_REVIEW                  (Maker self-pickup)
            --> REVIEWED             (Maker submits remarks)
                --> [Checker picks up -- checker_id assigned]
                      --> APPROVED   (Checker approves)
                          --> SENT_TO_CA
                              --> ISSUED
                              --> PENDING --> ISSUED / FAILED
                              --> FAILED  --> Admin retry --> SENT_TO_CA
                      --> REJECTED   (Checker rejects)
                          --> IN_REVIEW  (Admin reassigns new Maker)
                          --> CLOSED    (Admin closes)
            --> RETURNED             (Maker returns)
                --> IN_REVIEW        (Admin reassigns new Maker)
                --> CLOSED           (Admin closes)

  Separation of Duties -- Enforcement Rules (DUAL mode)
  -------------------------------------------------------

  Rule                                      Enforcement
  ----------------------------------------  ------------------------------------
  Maker cannot be Checker for same request  maker_id != currentUser.id checked
                                            at Checker pickup; 403 PKI_APR_005
                                            if violated

  Requestor cannot be Maker or Checker      requestor_user_id != currentUser.id
                                            checked at pickup; 403 PKI_APR_006
                                            if violated

  Checker cannot approve without being      checker_id == currentUser.id
  assigned                                  required at approve; 403 PKI_APR_004
                                            if violated

  Maker cannot skip review and approve      Server rejects /approve if called by
  directly in DUAL mode                     maker_id when mode == DUAL and
                                            status == IN_REVIEW

================================================================================
  12.  CA INTEGRATION AND ISSUANCE STATES             [CHANGED v1 -- C-14]
================================================================================

  NOTE: The previous design had only two CA outcomes: ISSUED and FAILED.
  Enterprise CAs (including WLCA) process requests asynchronously -- the CA
  acknowledges the request immediately but the certificate may be issued
  seconds to minutes later. This section defines the three expected CA
  outcomes and the async callback mechanism.

  12.1  CA Dispatch Flow
  -----------------------

  When a request reaches APPROVED status, the system dispatches it to the CA:

    [APPROVED]
        |
        | system dispatches to CA
        v
    [SENT_TO_CA]
        |
        +--[CA responds synchronously with cert]----> [ISSUED]
        |
        +--[CA acknowledges, processing async]-------> [PENDING]
        |                                                  |
        |                                          +-------+-------+
        |                                          |               |
        |                                       [ISSUED]       [FAILED]
        |                                     (callback)      (callback)
        |
        +--[CA returns error immediately]-----------> [FAILED]

  12.2  Three Expected CA Results
  ---------------------------------

  CA Result  RA Status  Description
  ---------  ---------  -------------------------------------------------------
  ISSUED     ISSUED     CA responded synchronously with a signed certificate.
                        Certificate is immediately stored and available for
                        download.

  PENDING    PENDING    CA acknowledged the request and queued it for
                        processing. RA waits for the CA to call back via
                        POST /api/ra/ca/callback.

  FAILED     FAILED     CA returned an error -- invalid CSR, policy violation,
                        CA system error, or timeout. Admin reviews and may
                        retry.

  12.3  Admin Retry on FAILED
  ----------------------------

    POST /api/ra/requests/{requestId}/retry
    Auth: ROLE_ADMIN

    - status --> SENT_TO_CA again
    - System re-dispatches to CA
    - If CA still unavailable: status --> FAILED again
    - Admin may retry multiple times or close permanently


================================================================================
  13.  MODE-SWITCH RULES
================================================================================

  When an Admin changes the workflow configuration mapping for a profile,
  only new pickups are affected. Requests already in-flight continue under
  the configuration that was active at the time of their pickup -- stored in
  approval_mode_at_pickup.

  Rule 1 -- SINGLE --> DUAL Config Switch

  In-flight Status           Behaviour
  -------------------------  --------------------------------------------------
  SUBMITTED (not picked up)  Next pickup resolves the new DUAL config.
                             Follows DUAL flow.

  IN_REVIEW (reviewing)      Continues under SINGLE mode.
                             approval_mode_at_pickup = SINGLE.
                             Operator uses /approve directly.

  APPROVED, ISSUED, CLOSED   No change. Already past approval stage.

  ----

  Rule 2 -- DUAL --> SINGLE Config Switch

  In-flight Status           Behaviour
  -------------------------  --------------------------------------------------
  SUBMITTED (not picked up)  Next pickup resolves the new SINGLE config.
                             Follows SINGLE flow.

  IN_REVIEW (Maker picked    approval_mode_at_pickup = DUAL is locked.
  up under DUAL)             Operator must use /review to submit to Checker.
                             Cannot skip to /approve.

  REVIEWED (awaiting         Must still have Checker. Maker already submitted.
  Checker)                   Cannot skip Checker step even though config
                             changed. System enforces: "Request was reviewed
                             under DUAL mode. Checker decision is required."

  APPROVED, ISSUED, CLOSED   No change.

  ----

  Rule 3 -- General Principles

  - The approval_mode_at_pickup column on each request locks the mode at
    pickup time.
  - Config changes apply to future pickups only.
  - In-flight requests complete under the mode they started with.

  PKI_APR_002   403   Cannot process your own request
  PKI_APR_003   403   Only Admin can perform this action
  PKI_APR_004   403   Only the assigned operator can perform this action
  PKI_APR_005   403   Maker cannot act as Checker. A different operator must
                      perform the Checker role.  (DUAL separation of duties)
  PKI_APR_006   403   Requestor cannot be Maker or Checker
  PKI_APR_007   404   Operator not found
  PKI_APR_008   400   Remarks are required for this workflow configuration
  PKI_APR_009   409   Request already picked up by another operator
  PKI_APR_010   400   Return reason is required
  PKI_APR_011   400   Invalid or inactive workflow configuration
  PKI_APR_013   400   Operator has reached the maximum pending request limit
  PKI_APR_014   400   No active workflow configuration found for this profile
                      [CHANGED v1 -- C-13]
  PKI_APR_015   400   Maker cannot approve directly in DUAL mode. Submit review
                      remarks via /review endpoint.  [CHANGED v1 -- C-11]

  NOTE: PKI_APR_012 removed  [CHANGED v1 -- C-11]:
    This error previously indicated that a DUAL mode API was called while the
    system was in SINGLE mode, or vice versa. With the unified /pickup and
    /approve endpoints that route server-side based on request state and caller
    role, this error code is no longer needed.

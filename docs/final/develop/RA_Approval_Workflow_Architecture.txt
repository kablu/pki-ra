  1. CSR INTAKE — REQUEST RECEPTION & STORAGE
================================================================================

  This is the ENTRY POINT of the entire RA system.
  Before any approval workflow starts, the CSR must be received,
  validated, stored, and assigned an initial transition status.
  The approval workflow DEPENDS ON this initial status.


  1.1 RA ENDPOINT — CSR SUBMISSION
  ================================================================

  API:    POST /api/ra/requests
  Auth:   Any authenticated user or system (via REST / EST / SCEP / CMP)

  The RA exposes a single endpoint that accepts certificate requests
  in PKCS#10 / CSR encoded format along with additional attributes.

  REQUEST FORMAT:

    Content-Type: application/json

  1.3 INITIAL TRANSITION STATUSES (before approval workflow)
  ================================================================

  When a CSR request arrives, it goes through these statuses
  BEFORE the approval workflow even starts:

    Client sends CSR
         |
         v
    [RECEIVED]  ← request saved to DB, raw CSR stored
         |
         v
    7-Layer Validation runs
         |
         +----------+----------+
         |                     |
         v                     v
    [VALIDATED]           [VALIDATION_FAILED]
    All 7 layers passed   One or more layers failed
         |                     |
         v                     v
    [SUBMITTED]           Request saved with
    Ready for approval    failure reason.
    workflow to start     Admin/operator can see
         |                why it failed.
         v
    Approval workflow
    begins here
    (SUBMITTED → IN_REVIEW → ...)


  STATUS DEFINITIONS (pre-approval):

  +-----------------------+-----------------------------------------------+
  | Status                | Description                                   |
  +-----------------------+-----------------------------------------------+
  | RECEIVED              | CSR received by RA endpoint. Raw request      |
  |                       | saved to csr_requests table. Validation       |
  |                       | has NOT started yet.                          |
  +-----------------------+-----------------------------------------------+
  | VALIDATED             | 7-layer validation PASSED. CSR is technically |
  |                       | correct, cryptographically valid, and         |
  |                       | policy-compliant. Transitions immediately     |
  |                       | to SUBMITTED.                                 |
  +-----------------------+-----------------------------------------------+
  | VALIDATION_FAILED     | 7-layer validation FAILED. CSR has issues     |
  |                       | (weak key, invalid DN, policy violation,      |
  |                       | duplicate, etc.). Stored with failure reason.  |
  |                       | Does NOT enter approval workflow.              |
  |                       | Client must fix and resubmit new CSR.          |
  +-----------------------+-----------------------------------------------+
  | SUBMITTED             | Validation passed. Request is now in the       |
  |                       | approval pool. This is where the approval      |
  |                       | workflow BEGINS. Operators can pick up.        |
  |                       | Admin can assign. Status visible to everyone.  |
  +-----------------------+-----------------------------------------------+

  IMPORTANT:
    The approval workflow (Maker-Checker process) only operates on
    requests that have reached SUBMITTED status. Requests stuck in
    RECEIVED or VALIDATION_FAILED never enter the approval pipeline.


  1.4 COMPLETE STATUS FLOW (intake + approval combined)
  ================================================================

    [RECEIVED] → [VALIDATED] → [SUBMITTED] → [IN_REVIEW] → ...
                       |
                       v
              [VALIDATION_FAILED]
              (dead end — resubmit)

    Full chain:
      RECEIVED → VALIDATED → SUBMITTED → IN_REVIEW →
        SINGLE: → APPROVED → ISSUED
                → REJECTED → (Admin: reassign or close)
                → RETURNED → (Admin: reassign or close)
        DUAL:   → REVIEWED → APPROVED → ISSUED
                            → REJECTED → (Admin: reassign or close)
                → RETURNED → (Admin: reassign or close)

================================================================================
  2. APPROVAL WORKFLOW — OVERVIEW (starts from SUBMITTED status)
================================================================================

  The approval workflow is FULLY CONFIGURABLE by Admin:

  MODE 1 — SINGLE OPERATOR (Maker only):
    Admin configures: approval_mode = SINGLE
    One operator reviews, verifies, and approves/rejects the CSR.
    No second operator (Checker) needed.

  MODE 2 — DUAL OPERATOR (Maker + Checker):
    Admin configures: approval_mode = DUAL
    Maker reviews and submits remarks.
    Checker (different operator) accepts or rejects.
    Separation of duties enforced — Maker cannot be Checker.

  KEY DESIGN PRINCIPLES:
    - Admin CONFIGURES the process (how many operators needed)
    - Admin MONITORS all records and their status
    - Operators work INDEPENDENTLY (pick up CSR requests themselves)
    - Admin CAN optionally assign a specific request to a specific operator
    - All records visible to Admin AND all operators (with status)
    - Every record maintains full TRANSITION STATUS history
    - Admin can FILTER any record by any criteria at any time
    - Configuration is changeable at any time via Admin dashboard

  4. STATE MACHINE
================================================================================

  MODE 1 — SINGLE OPERATOR:

    [SUBMITTED] → Operator picks up (or Admin assigns)
         |
         v
    [IN_REVIEW] → Operator reviewing
         |
         +----------+----------+----------+
         |                     |          |
         v                     v          v
    [APPROVED]            [REJECTED]  [RETURNED]
         |                     |          |
         v                     v          v
    Send to CA           Admin sees   Admin sees
         |               (reassign    (reassign
         +--------+       or close)    or close)
         |        |
         v        v
    [ISSUED]  [FAILED]


  MODE 2 — DUAL OPERATOR (Maker + Checker):

    [SUBMITTED] → Maker picks up (or Admin assigns)
         |
         v
    [IN_REVIEW] → Maker reviewing
         |
         +----------------+--------------------+
         |                                     |
         v                                     v
    [REVIEWED]                            [RETURNED]
    Maker submitted remarks               Maker sent back to Admin
         |                                     |
         v                                     v
    Checker picks up                      Admin (reassign or close)
         |
         +----------+----------+
         |                     |
         v                     v
    [APPROVED]            [REJECTED]
         |                     |
         v                     v
    Send to CA            Admin sees
         |                (reassign or close)
         +--------+
         |        |
         v        v
    [ISSUED]  [FAILED]


  STATE DEFINITIONS:

  +-----------------+---------------------------------------------------+
  | State           | Description                                       |
  +-----------------+---------------------------------------------------+
  | SUBMITTED       | CSR received, validation passed.                  |
  |                 | Visible to all operators and Admin.               |
  |                 | Available for pickup or assignment.                |
  +-----------------+---------------------------------------------------+
  | IN_REVIEW       | An operator has picked up / been assigned this     |
  |                 | request and is currently reviewing it.             |
  |                 | In SINGLE mode: this operator will approve/reject.|
  |                 | In DUAL mode: this is the Maker.                  |
  +-----------------+---------------------------------------------------+
  | REVIEWED        | DUAL mode only. Maker submitted review with        |
  |                 | remarks. Waiting for Checker to pick up.          |
  +-----------------+---------------------------------------------------+
  | RETURNED        | Maker/Operator sent request back to Admin.         |
  |                 | Admin can reassign or close permanently.           |
  +-----------------+---------------------------------------------------+
  | APPROVED        | Approved (by single operator or Checker).           |
  |                 | Sending to CA for signing.                         |
  +-----------------+---------------------------------------------------+
  | REJECTED        | Rejected (by single operator or Checker).           |
  |                 | Goes back to Admin for reassign or close.          |
  +-----------------+---------------------------------------------------+
  | CLOSED          | Permanently closed by Admin. True final state.     |
  +-----------------+---------------------------------------------------+
  | ISSUED          | CA signed successfully. Certificate active.        |
  +-----------------+---------------------------------------------------+
  | FAILED          | CA signing failed. Admin can retry.                |
  +-----------------+---------------------------------------------------+

  VALID TRANSITIONS:

  +-------------------+---> +-------------------+--- Who / When --------+
  | From              |     | To                |                        |
  +-------------------+     +-------------------+------------------------+
  | SUBMITTED         | --> | IN_REVIEW         | Operator picks up      |
  |                   |     |                   | or Admin assigns       |
  | IN_REVIEW         | --> | APPROVED          | SINGLE mode: operator  |
  |                   |     |                   | approves directly      |
  | IN_REVIEW         | --> | REJECTED          | SINGLE mode: operator  |
  |                   |     |                   | rejects directly       |
  | IN_REVIEW         | --> | REVIEWED          | DUAL mode: Maker       |
  |                   |     |                   | submits remarks        |
  | IN_REVIEW         | --> | RETURNED          | Operator returns to    |
  |                   |     |                   | Admin (any mode)       |
  | REVIEWED          | --> | APPROVED          | DUAL: Checker accepts  |
  | REVIEWED          | --> | REJECTED          | DUAL: Checker rejects  |
  | RETURNED          | --> | IN_REVIEW         | Admin reassigns        |
  | RETURNED          | --> | CLOSED            | Admin closes           |
  | REJECTED          | --> | IN_REVIEW         | Admin reassigns        |
  | REJECTED          | --> | CLOSED            | Admin closes           |
  | APPROVED          | --> | ISSUED            | CA signs OK            |
  | APPROVED          | --> | FAILED            | CA error               |
  | FAILED            | --> | APPROVED          | Admin retries          |
  +-------------------+     +-------------------+------------------------+


================================================================================
  5. FLOW — SINGLE OPERATOR MODE
================================================================================

  Step 1: Client submits CSR
    API: POST /api/ra/requests
    → status = SUBMITTED
    → visible to ALL operators + Admin

  Step 2: Operator picks up request (SELF-PICKUP)
    API: POST /api/ra/requests/{id}/pickup
    Auth: ROLE_OPERATOR
    → status = IN_REVIEW
    → picked_up_by = current operator
    → Other operators see: "In review by priya.patel"

    OR Admin assigns (ADMIN-ASSIGN / HYBRID):
    API: POST /api/ra/requests/{id}/assign
    Auth: ROLE_ADMIN
    Body: { "operatorId": 5 }
    → status = IN_REVIEW, assigned_to_id = 5

  Step 3: Operator reviews and decides
    API: POST /api/ra/requests/{id}/approve
    Body: { "remarks": "CSR verified. All checks passed." }
    → status = APPROVED → auto-issue via CA

    OR
    API: POST /api/ra/requests/{id}/reject
    Body: { "remarks": "Domain not in approved list." }
    → status = REJECTED → goes to Admin dashboard

    OR
    API: POST /api/ra/requests/{id}/return
    Body: { "reason": "Key size too small, need clarification." }
    → status = RETURNED → goes to Admin dashboard


================================================================================
  6. FLOW — DUAL OPERATOR MODE (Maker + Checker)
================================================================================

  Step 1: Client submits CSR
    → status = SUBMITTED

  Step 2: Maker picks up or Admin assigns
    API: POST /api/ra/requests/{id}/pickup (or /assign)
    → status = IN_REVIEW (Maker = current operator)

  Step 3: Maker reviews and submits remarks
    API: POST /api/ra/requests/{id}/review
    Body: { "remarks": "CSR verified. Recommend approval." }
    → status = REVIEWED
    → Visible to all operators EXCEPT Maker (for Checker pickup)

    OR Maker returns:
    API: POST /api/ra/requests/{id}/return
    → status = RETURNED → Admin dashboard

  Step 4: Checker picks up reviewed request
    API: POST /api/ra/requests/{id}/pickup-check
    Auth: ROLE_OPERATOR (must NOT be the Maker)
    → Checker sees Maker's remarks

  Step 5: Checker decides
    API: POST /api/ra/requests/{id}/accept
    Body: { "remarks": "Agreed with Maker." }
    → status = APPROVED → auto-issue

    OR
    API: POST /api/ra/requests/{id}/reject
    Body: { "remarks": "Domain issue found." }
    → status = REJECTED → Admin dashboard

  SEPARATION OF DUTIES (DUAL mode):
    The RA Operator who acts as Maker is STRICTLY PROHIBITED
    from acting as Checker for the same request. This is enforced
    at the API level. Violation returns 403 PKI_APR_005.

  8. TRANSITION STATUS HISTORY (per record)
================================================================================

  Every status change creates a history entry.
  Admin and Auditor can see the full trail.

  Table: certificate_request_transitions

  +----------------------------+---------------+-----+-----------------------+
  | Column                     | Type          | Null| Purpose               |
  +----------------------------+---------------+-----+-----------------------+
  | id                         | BIGINT PK     | NO  | Auto-increment        |
  | request_id                 | BIGINT FK     | NO  | → certificate_requests|
  | from_status                | VARCHAR(20)   | YES | Previous status       |
  |                            |               |     | (NULL for first entry)|
  | to_status                  | VARCHAR(20)   | NO  | New status            |
  | changed_by_id              | BIGINT FK     | NO  | → users.id            |
  | changed_by_role            | VARCHAR(20)   | NO  | ADMIN / OPERATOR /    |
  |                            |               |     | SYSTEM                |
  | remarks                    | VARCHAR(2000) | YES | Remarks / reason      |
  | created_at                 | DATETIME(6)   | NO  | When transition       |
  |                            |               |     | occurred              |
  +----------------------------+---------------+-----+-----------------------+

  Example history for one record:

  +----+--------+-----------+-----------+-------------+--------------------+
  | #  | From   | To        | By        | Role        | Remarks            |
  +----+--------+-----------+-----------+-------------+--------------------+
  | 1  | NULL   | SUBMITTED | rahul     | USER        | CSR submitted      |
  | 2  | SUBMIT | IN_REVIEW | priya     | OPERATOR    | Picked up          |
  | 3  | IN_REV | REVIEWED  | priya     | OPERATOR    | CSR verified. OK.  |
  | 4  | REVIEW | APPROVED  | vikram    | OPERATOR    | Agreed. Approved.  |
  | 5  | APPROV | ISSUED    | system    | SYSTEM      | Cert: 4F2A1B3C...  |
  +----+--------+-----------+-----------+-------------+--------------------+

  API to view transition history:
    GET /api/ra/requests/{id}/history
    Auth: ROLE_ADMIN or ROLE_AUDITOR
